# 公开输出诊断与失败教训 V3

这是 V1/V2 之后的独立开发实验，旧成绩、请求预算和报告不变。只借用当前薄 LLM 客户端及笔记领域方法，不增加 Agent 框架，不接入生产记忆。

## 预先固定的问题与预算

问题 A：在相同输入下，增加请求的输出预算是否改变空输出、长度终止、完整 JSON 的观察结果？

| 输入 | 请求顺序 | 用途 |
|---|---|---|
| 简单 JSON 控制 | 1200 → 3600 | 排除所有输入都无法公开输出的粗粒度问题 |
| V2 局部修改的完整公开输入 | 3600 → 1200 | 重放以前发生截断的输入 |
| V2 进度改写的完整公开输入 | 1200 → 3600 | 重放以前发生空输出的输入 |

每格一次请求；配对内消息逐字一致，模型、temperature=0.1、reasoning_effort=low、JSON mode 均一致，只改变 max_tokens。顺序提前固定；仅一个样本，随机性、时间与顺序仍混杂，不能估计成功率或证明唯一原因。3600 请求是独立对照，不是遇到失败后临时重试。JSON 完整不表示经验正确；空文本不能当成明确弃答。

固定输入文件仅保存简单控制和 V2 的公开消息，未携带旧输出、语义结论、目标任务、G 卡或 oracle。准备时复核原报告哈希、消息与当时 request input 一致、消息指纹一致；执行时复核冻结固定输入自身。历史观察 ID 不再有在线来源，不用于候选入库或证据验证。

问题 B：单独提供版本冲突的实际失败过程，模型能否归纳一条受证据约束的停止教训？

只执行 `source-version-b` 的合成环境领域动作，产生新的真实公开回执。单次请求，固定 3600 输出预算，不受问题 A 的成绩路由影响。选用此前诊断过的来源，是开发试验，不是留出评测。输入包括全部该失败过程及共同工具契约；没有手写正确教训或恢复答案。

总计最多 7 次预约/实际请求，最大请求输出量 `3 × (1200 + 3600) + 3600 = 18000`；每次 45 秒，`max_attempts=1`。网络、空输出、截断、解析和校验失败均占原槽位，不修卡、不追加请求。上界不包含输入 token、费用和未报告用量。

## 逐项引用契约

`lesson:null` 表示明确弃答。否则 lesson 只有 `record_type=failure_lesson`、scope 和 claims。固定三项：`observed_failure`、`stop_condition`、`uncertainty`，分别最多100字符、各1–2项证据。每项引用含实际 observation_id、从公开事件根开始的 JSON Pointer、该字段的原始标量 value。保存经过模型输出的文字，不人工补充或改写。

程序检查类型、字段集合、长度、逐项引用、公开路径存在、标量值和类型完全相同、当前来源归属、领域证据仍在线、历史身份不进入做法。失败观察必须引用真实 `result.ok=false` 的事件。然后用临时笔记库保存并重开核对，运行后关闭来源。

这只能验引文，不能证明中文主张与证据有逻辑蕴含关系。引用冲突的 `write_observed=false` 可以支持未保存，却不能自动证明“再 preview 就获取最新基底”。离线反例专门保留这种结构通过、语义待审的情况。scope、停止建议及未知边界仍需独立定性复核；人类打分和自动语义分数保持 null。

## 冻结与运行

运行器：[eval_procedural_memory_diagnostics.py](../scripts/eval_procedural_memory_diagnostics.py)。默认只写计划，`--prepare-sources` 零模型执行，`--live` 需明确连接与专用进程环境凭据，评测本身不读取 `.env`。

源码冻结使用显式 `diagnostics_v1` profile/schema2：原13文件加诊断运行器和固定公开输入，共15文件。原 schema1/13文件的验证契约保持。子进程从副本启动，manifest哈希由父进程绑定，执行前、每次请求前、结束后再验证；报告实际脚本、LLM、评测和领域模块路径。副本没有生产数据库、`.env` 或 oracle。

结果分别报告公开输出完成情况与失败教训定性判断，不把诊断对照计成语义收益。只有教训质量稳定后，才冻结方案并用新来源与留出目标检验行为迁移。
