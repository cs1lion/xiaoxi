# 陪伴角色技术路线评估

日期：2026-10-14。根据用户提出的视觉、动作、Agent 与引擎路线，对当前工作目录源码和实际模型进行只读核查。本文是路线评估；没有因此修改模型、渲染器、语音链路或调用真实供应商。本次源码核查也不替代真机性能、听感和跨日使用验收。

## 判断

路线整体可行，但技术名称应服务于具体体验。当前最合适的主线仍是 Three.js + three-vrm：先确定脸部和眼睛的审美目标，修正可复查的光影问题，再补实际可见的头发动态与躯干呼吸。与此同时保留现有说话、手势与打断行为，后续根据真实延迟与记忆质量决定 Agent 的升级。

SDF、52 个 ARKit 通道、复杂布料、向量加图谱及更重的引擎，各自都有资产、性能和验证成本。它们可以进入后续阶段，当前不宜把它们当成第一版角色成立的共同前置条件。

## 现状对照

| 用户提出的能力 | 当前可依据的事实 | 主要缺口与判断 |
| --- | --- | --- |
| Cel-Shading、脸部法线 | Daily 脸、眼睛、发衣已经使用 MToon。原脸法线保留，脸材质有 shading-shift 纹理和轮廓宽度遮罩 | 先做侧光/转头对照，定位光照、阴影边界、贴图与法线贡献。球面法线可作为候选，不能保证所有角度都像手绘；本轮没有证据要求直接换 shader |
| 虹膜层次、高光与 LookAt | 有实际 VRM LookAt、微眼跳和眼头协调；高光控制已有层的可见度。眉高、下睑与笑眼已有独立候选资产 | 多层虹膜、独立瞳孔及新的反光材质尚未完成。标准 Daily 和增强候选能力需要逐一核对，不能把全部候选能力视作当前页面已合并 |
| SDF 面部阴影、发丝高光、细内描边 | 有 MToon 阴影与轮廓；新头发使用分色发片 | 没有完整方向驱动的脸部 SDF、各向异性高光或定制内线管线。需要独立纹理/遮罩、稳定坐标及资产调校，先明确画风与具体缺陷 |
| 弹簧骨与布料 | VRM 管理器可更新保留的弹簧链 | Daily 保留 9 条旧链、28 节点，但它们对活动索引引用顶点的正权重命中为零。新短发片全部绑定 head，当前没有可见发丝/衣摆物理；优先给少量前发建立实际骨链与蒙皮 |
| 分层待机与微动作 | 已有随机眨眼、微眼跳、低频值噪声头动、眼头时序、四指/拇指与肩胸动作配合 | `ParamBreath` 尚未映射为 VRM 躯干呼吸。耳廓、随机摆指和大幅重心变化优先级较低；半身陪聊先补有目的的小幅动作和安静停留 |
| 音素口型与情绪 | 汉字→拼音声韵母→共发音时间轴，按实际音频时钟采样；RMS 用于调幅。已有眉眼、脸红、嘴角等通道 | 音素时间由文本和整句时长估计，仍需真实时间对齐。FaceLandmarker 能读 52 系数不等于角色有 52 独立形变；标准 Daily 43 个自定义 morph、下睑候选 51 个，命名和含义均不等于 ARKit |
| 状态机与 IK 接触 | 倾听、思考、准备、实际播放和打断已有眼神/表情时序；手臂从当前姿态平滑衔接并恢复 | 尚无撑桌、托腮、触屏的 IK 和接触求解。需环境坐标、接触点、姿态资产、限位及手部/衣料处理，适合在自由手势稳定后单独实施 |
| 低延迟语音 | 普通陪聊已有流式 LLM 与并行句级 TTS；连续监听、播放队列和旧轮次取消已有实现。思考约 .35 秒后有眼神/表情反馈 | 主聊天在 `audio_end` 后才整段 ASR，TTS 收齐每句音频后交付。独立英语翻译页有双向流式 ASR 适配，尚未接入普通中文陪聊，也未完成真实供应商验收 |
| 300–500 ms 垫场与情感语音 | 有非语音思考反馈、情绪标签与 TTS 指令 | 没有已验证的 300–500 ms 首声目标、轻嗯音频或显式笑声/呼吸控制。应区分等待反馈和真实回复首声；不以固定垫场掩盖无法理解或较长延迟 |
| 性格与长短期记忆 | persona 契约、示例与动态回应策略；SQLite 四类长期记忆，原话证据、纠正/删除、版本及后台抽取；字符 n-gram TF-IDF 检索 | 近期历史是原话截取，未总结压缩；没有 embedding 检索/知识图谱，也没有专用微调或快慢模型路由。优先保证事实、来源、更新和接续质量，再按检索失败选择组件 |
| 屏幕与视觉上下文缓存 | 本地显式开启的 FaceLandmarker 面部镜像；共享音频翻译可请求屏幕权限 | 没有 Agent 图像输入通路、视觉摘要、关键帧缓存或按需回看。共享音频入口不编码或上传视频。用户描述的摘要+外部帧缓存方向可行，需按场景明确触发、时效与来源 |

MToon 加载器会移除普通 PBR 的 metalness/roughness 参数，因此不能仅根据 GLB 中的 PBR 数值判断当前“塑料感”的来源。材质是否好看仍需实际画面比较。

## 推荐实施顺序与验收

1. **固定视觉目标与光影基线。** 在同一模型、镜头、表情和灯光下检查正面、左右转头、侧光、眨眼和开口。先调材质/光照/阴影边界，确认必要性后再试局部法线或 SDF。验收同时看脸部干净程度、眼鼻轮廓保留和动态中间帧；不只比较正面静帧。
2. **补真实可见的陪伴动态。** 先完成前发骨链与蒙皮，再补小幅躯干呼吸、倾听到思考的姿态过渡和手型意图。随机变化围绕当前状态使用，保留安静段。检查持续观看、侧视、打断与恢复；不通过扩大动作掩盖僵硬。
3. **测量并处理语音瓶颈。** 真机分别测停嘴→端点、ASR、模型首段、TTS、解码、实际听见首声的 P50/P95，以及打断停止和句间接缝。随后决定是否把流式 ASR 接入普通陪聊、改 TTS 音频块交付或做模型路由；同步提升口型时间对齐。等待表情沿真实状态触发，发声反馈纳入同一可取消播放链。
4. **证明跨日接续和记忆质量。** 用共同经历、明确纠正、习惯变化和删除后回看等场景验收，保留原话来源。摘要保留可回溯证据；语义检索只在已有失败样本支持时引入，图关系只在关联查询确有需要时增加。主动提起事件需要明确的时间与上下文依据。
5. **按需视觉，再做环境接触。** 从用户选定的单个屏幕/窗口开始，以问题或任务变化触发截图、摘要和关键帧引用；保留帧时间、来源及失效信息。先做一次能定位来源的“看当前画面”，再考虑回看与长时缓存。托腮/撑桌等动作以单一接触场景验证 IK、限位与服装间距。

## 技术选型

| 路线 | 对本项目的建议 | 需要核实的边界 |
| --- | --- | --- |
| Three.js / WebGL + VRM | 当前主线，复用已有表情、口型、动作与音频时钟，最容易做逐项对照 | 可做 SDF、材质定制与轻量动态，成本来自实现和资产；内存/功耗需实测，Electron 的浏览器进程也有固定开销 |
| Unity | 进入复杂 IK、动画制作、碰撞和独立桌面应用需求后，做一个相同场景的对照原型 | URP 与具体卡渲插件的渲染管线、版本及许可分别核对，NiloToon/lilToon 不应视作可随意互换的组合；模型和美术仍需适配 |
| Unreal Engine | 适合需求明确的高规格演出或复杂场景，当前常驻半身陪伴优先级低 | 画面质量取决于美术与卡渲方案，不能从引擎名直接推出；重点验证常驻资源、冷启动和分发成本 |

当前迁移引擎会同时改变渲染、动画、资源加载和音频同步，需要重新验收已有成果。先在现有引擎验证目标画面，能形成更可靠的迁移依据。
