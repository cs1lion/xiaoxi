# 阿栖 · 安静的陪伴空间

## 产品判断

用户来到这里不是操作控制台，而是聊天、整理日常、被理解。第一次成功是：不需要读说明就能发出一句话，并看懂阿栖正在回应。视觉不能掩盖真实的连接状态，也不能诱导默认开启麦克风或摄像头。

参考：[Joye 的组件 → 流程 → 产品设计文章](https://www.joyehuang.me/notes/1026-ui-taste)。采用其中的组件语义、完整首次使用流程、少量点睛动效、可点击区域、等宽数字及高频交互克制原则；不是复制某个组件库的模板。

## 视觉约定

- 暖白 `#f5f5ef`：阅读背景；苔绿 `#456e54`：主操作；墨绿灰 `#303d36`：正文。
- 浅草绿径向渐变仅作为聊天空间的环境色，不播放循环背景动画。
- 衬线开场标题强调温度，正文保持系统无衬线字体；无需下载字体。
- 面板圆角 16px，输入区 19px；低对比边框而非堆叠阴影。
- 状态不只靠颜色：在线、思考、错误均有文本。时间和记忆计数使用等宽数字。

## 层级与首次使用

1. 打开页面：看到邀请式空状态、三个可选择的聊天开头，以及固定输入区。
2. 点击开头：只写入草稿，用户仍可修改，不自动调用模型。
3. Enter / 发送：明确提交；中文输入法选词不误发送。
4. 首条真实消息到达：空状态退场，聊天成为主内容。
5. 记忆常驻侧栏，任务与提醒、声音与形象渐进展开；不再有遮挡顶栏的浮动任务框。
6. 移动端用“记忆与偏好”展开非模态侧栏；Esc 关闭并归还焦点。对话开始后收起移动端装饰形象，避免遮字。

## 小惊喜与边界

- 开场 600ms 轻淡入，消息 220ms；选择卡片箭头轻移。不阻塞高频发送。
- 输入区聚焦有淡淡边框和光晕，提示“可以开始说”。
- `prefers-reduced-motion` 关闭 CSS 动效。现有角色渲染引擎的持续动作不属于本次 CSS 开关，需要单独评估。
- Switch 保留真实可聚焦 input；按钮原则上至少 44px 高。
- 连接不可用时保留草稿并显示说明，不清空后丢失。
- 任务操作继续走原接口和确认参数，没有视觉上的假成功。

### 可复用的设计思路

1. **渐变像环境光，不像海报。** 用相邻色相、低透明度、大范围渐变，放在留白区域；正文、表单和错误信息仍有稳定底色。
2. **一个空间一个主动作。** 聊天页主按钮是发送；实验配置折叠，危险操作弱化但不隐藏。不要让所有按钮都有品牌填色。
3. **小惊喜服务于意图。** 箭头微移表示可以开始；保存成功有真实回执；读旧消息时不抢滚动位置。避免粒子、跑马灯、跟随光标争抢对话注意力。
4. **轻盈来自删减，不是降低可读性。** 少边框、适当留白、明确标题可以减轻拥挤感；不能靠把说明文字调到极淡实现“高级”。
5. **动效有预算。** 本版开场 600ms、消息 220ms、控件约 180–200ms；键盘开关和发送不增加人为等待。不把整段回复二次打字播放。
6. **状态设计比正常态更重要。** 首次空白、加载、失败、断线、取消、长文本都应有明确行为；成功提示必须与服务结果一致。

### 未采用的方向与原因

- 暗黑霓虹与高饱和多色渐变：更像技术演示，偏离日常陪伴。
- 全屏玻璃拟态：可能降低长文本和表单的可读性。
- 大幅视差、自动轮播、全页 stagger：对高频聊天没有相应收益。
- 直接搬入一整套 React 特效库：现有界面是原生模块，收益不足以抵消迁移和依赖成本。

这些是本项目的设计判断，不是说上述视觉语言在其他产品里不好。

### 人工视觉验收清单

- 桌面开场：第一眼是否看见聊天邀请和输入框，而不是偏好设置？
- 手机开场：角色是否遮挡建议卡片？标题换行和留白是否自然？
- 长对话：气泡行宽是否舒适？回到最新按钮是否遮挡当前阅读内容？
- 偏好展开：中文字号、表单间距、错误说明是否易读？
- 实际中文系统字体：衬线标题是否呈现预期温度，而不是生硬或拥挤？

用户可先看截图再决定是否继续调整配色或密度；没有视觉审阅证据前，不以自动布局测试代替审美验收。

## 验证与当前限制

运行 `node scripts/test-ui-browser.mjs`，使用现有 `http://127.0.0.1:8000/` 服务；WebSocket 使用受控消息，不请求付费模型，不创建任务或记忆。测试使用真实应用消息渲染器。

覆盖开场、草稿、IME、发送、流式响应、320/390/768px 无页面横向溢出、移动侧栏、Esc 焦点、减少动态、记忆开关键盘焦点、浏览器错误。

截图与报告写入 `eval/ui/`。当前模型不支持图像输入，read_image 无法打开截图，因此不能将已生成截图声称为人工视觉审阅通过。

追加验收（第 2–8 轮）：
- 长消息历史在 320/390/768px 内部滚动，输入框保持视口内；没有页面横向溢出。
- 移动端连续两次行动确认可展开侧栏、滚动到卡片并获取焦点。
- 任务服务 404 有中文说明和重试，失败重试保留说明，恢复不重复挂载。
- 记忆保存、设置、删除、刷新失败不展示假成功；输入和已加载记忆得到保留。元数据使用 textContent。
- `node scripts/test-voice-ui.mjs` 使用模拟麦克风，覆盖空格录音、松开释放轨道、等待权限时取消、拒绝权限反馈、连续对话关闭及停止按钮的中断请求。
- 纯色 token 对比度：正文/背景 10.39:1，主按钮 5.76:1，侧栏次要文字调整后 4.82:1，占位文字调整后 4.93:1。这不是全页面 WCAG 审计。

第 12 轮接口契约验证：`python scripts/test_assistant_ui_contract.py` 使用真实 FastAPI 路由与隔离 SQLite，已通过 UTC 偏好、创建/完成任务、创建/取消提醒、列表结构和同源写入保护。没有启动新服务器，也没有写入生产数据。首次使用 Asia/Shanghai 时发现当前 Python 环境缺少可用的该 IANA 时区数据，接口返回 `unknown IANA timezone`；第 13 轮已补充 tzdata 依赖并更新锁文件，当前虚拟环境安装 tzdata 2026.5；真实路由的 UTC、Asia/Shanghai、America/New_York 偏好写入均通过，另有 15 项存储回归通过。该环境的时区数据缺失已解决；没有重启原有服务进程。

测试边界：现有任务偏好接口返回 404；浏览器回归模拟任务偏好/列表与记忆写入失败接口，不能视为真实任务端到端验收。语音测试使用假设备与受控 WebSocket，不能代表真实识别/合成质量。真实服务端到端集成验收仍未完成，独立于本次已确认的前端设计交付。

## 第 16 轮设计验收

用户查看最新桌面与手机预览后，明确选择「这版可以，保留设计」。本次前端设计目标据此收尾。此前用户要求「更鲜明、更有惊喜」，已增加暖杏色品牌点缀、标题手绘高亮和首张建议卡片的浅杏渐变；建议点击后提供草稿确认反馈，但绝不自动发送。

最终验证：浏览器回归覆盖草稿反馈、长历史滚动保留、返回最新、长字幕限高、移动输入字号与既有交互；第 16 轮重新生成干净预览并重跑模拟语音测试，通过。该视觉确认来自用户，不是当前模型读取图片后的结论。

明确保留的后续事项：当前运行服务的任务路由 404 尚未在原进程中解决；真实 ASR/TTS、iPhone 真机键盘与全面无障碍审计未验收。没有重启原服务，也没有将模拟测试描述为真实端到端通过。
