# 像素小镇 · 方向调研与建议

> **历史研究/提案（2026-10-19 标注）**：本文「不建议引 Phaser/Pixi、v1 用 Canvas 2D 手写渲染」的结论未被采纳。实际实现采用 **Phaser 3 + Vite + TypeScript**（`pixel-world/`），依据 `PROJECT_BRIEF.md:10` 的已确认决策；背景与 ADR 见 `docs/DECISION_TRAIL_20261019.md` D1。原文保留，不作删改。

2026-10-18 · 仅调研与提案，未改动任何代码

## 0. 一句话结论

**这个想法的价值不在"换成像素风"，而在于它第一次给了多 Agent 架构一个可读的空间形态**——
现在 9 个角色在界面上只能是一排 swimlane 卡片，在镇子里它们是不同的铺子，谁在干活一眼可见。
建议走「窗中镇」：像素世界占主舞台，纸张继续负责文字与回执，**状态机一条不改，只多一个渲染器**。

---

## 1. 先回答：为什么这个想法成立

### 1.1 产品其实已经是一台状态机，缺的只是一个可信的舞台

现有 `Commission` 状态集是固定的六阶段 + 归档（PROTOCOL §19）：

`drafting → briefing → running → blocked? → auditing → ready_to_report → done`

这六个阶段本身就是一出戏的六个场次：**接到活 → 分派 → 干 → 卡住 → 核对 → 交差 → 归档**。
现在的界面把这六个场次压成了卡片上的一个状态字（"进行中"）。像素世界做的事，
是把它还原成"发生在某个地方、由某个人做"的事件。

### 1.2 现有资产复用度

| 已有 | 在镇子里的角色 | 复用度 |
| --- | --- | --- |
| 花名册 9 角色（笔录官 / 营造匠 / 探马 / 真机 Claude / WorkBuddy / dsh…） | 镇上的铺子与店主 | 高，`agents_roster.yaml` 直接是设定集 |
| 六阶段状态机 + `step_idx` | 场次与进度 | 高，纯读 |
| `blocked_question`（一句话、二选一） | 店主跑到门口举牌问一句 | 高，正好是 `choice_pills` |
| `delivery` 三句话验收卡 | 交付箱吐出的回执 | 高 |
| `audit.layer` l1/l2 + `findings` | 账房里打回重做 | 高 |
| telemetry（tokens / ttft） | 铺子的烟囱、机器热度 | 中，需要视觉隐喻 |
| idle driver 的 energy 三段（drowsy / sleepy / dozing） | 她会困、会靠墙、会打哈欠 | 高，**这就是"她有自己的生活"的现成素材** |
| 三态 presence（灵动伴随 / 静默旁观 / 无痕闲聊） | 她在不在家、要不要打扰你 | 高 |
| 星图记忆 / 按天日记 / 心境偏置 | 夜空星座、书架、窗边的日记本 | 中，需要新资产 |

**结论：这不是重写，是给同一份真相加第三个渲染器。** 项目现在的分层恰好支持这一点：
`参数状态 → drivers → render/{svg,vrm}`。像素世界就是 `render/world`。

## 2. 标杆拆解（每个只偷一条，每个只避一坑）

### 2.1 Stardew Valley —— 偷"自由在结构里"，避"必须经营"

- 事实：16×16 图块，运行时 4 倍整数放大；农夫精灵 16×32（一宽两高）；一天十几分钟，凌晨两点前必须睡；
  图层顺序 Back / Buildings / Paths / Front / AlwaysFront；地形过渡用 47 块 blob 自动拼接。
- 可偷：**"cozy 不是没有目标，是目标由你选"**。社区中心给长期方向，告示板给短期提示，两边都不惩罚你忽略它。
- 要避：它的核心循环是**经营**（种地、浇水、养殖）。我们绝不能把"维护这个镇子"变成用户的新工作。

### 2.2 Generative Agents / Smallville —— 偷"记忆流 + 反思 + 计划"，避"为了模拟而模拟"

- 事实：25 个 LLM 智能体；完整记忆流 + 按新近度/重要性/相关性检索 + 周期性反思 + 每日计划；
  会自发扩散消息、约人、协调时间。
- 可偷：她"有自己的生活"的可信度来自**连续的记忆与计划**，而不是随机待机动画。
  我们已经有日记、心境、星图记忆——缺的是把它们变成"今天她打算做什么"。
- 要避：论文目标是"行为可信度"，代价是极其昂贵。我们的目标不是模拟社会，是**让工作过程可读**。

### 2.3 AI Town（a16z）—— 偷"技术选型的边界"，避"把模拟当产品"

- 事实：MIT，PixiJS 渲染 + Convex 做状态/事务/向量检索，地图走 Tiled 导出，角色定义在 `data/characters.ts`，约 11k stars。
- 可偷：**地图用 Tiled 画、用 JSON 导出**，美术与代码解耦，改场景不用改代码。
- 要避：它是个"AI 角色社交沙盒"，没有真实工作流。我们是相反的——**工作流是真的，世界只是它的投影**。

### 2.4 Habitica —— 反面教材，最重要的一条

- 事实：把待办变成 RPG；漏做每日任务会掉血、队友受牵连。社区反馈里最高频的退出原因就是
  "**游戏本身变成了另一份工作**"（要维护装备、宠物、职业、组队）、"漏一天就被惩罚"、界面过载。
- 我们要立的规矩：**世界不惩罚你、不要求你经营、不撒谎**（见 §3 铁律）。
  一旦"看镇子"比"看任务"更费神，这个方向就失败了。

## 3. 世界该怎么设计（不是照抄星露谷）

### 3.1 五条铁律

1. **世界不惩罚你。** 没有掉血、没有枯萎、没有连续登录。你没来，她只是在过日子。
2. **世界不要求你经营。** 不做种田/喂养/装修作为核心循环。布景是装饰，不是 KPI。
3. **世界不撒谎。** 每个动画都必须能追溯到一个真实字段。没活干就是没活干，不做"看起来很忙"的假动作
   （项目已有"不伪造业务成功"的铁律，这里是它的视觉版）。
4. **文字归纸，像素归生活。** 信息面板继续用现在这套暖纸宋体；像素只负责"正在发生什么"。
   这不是妥协——"一本手帐，中间开了一扇通往小镇的窗"本身就是很强的产品意象。
5. **三秒法则。** 任何时刻，三秒内能回答"我的事办到哪了"。世界是索引，不是迷宫。

### 3.2 你点名的四个状态，对应到真实字段

| 你说的 | 真实状态 | 世界里发生什么 | 现有组件 |
| --- | --- | --- | --- |
| 接任务 | `drafting → briefing` | 你往门口邮箱投一张便条；她把便条拆成三行，盖上章 | 派单意图 / thread proposals |
| 干活中 | `running`（`step_idx`） | 对应铺子亮灯：笔录官翻纸、营造匠敲钉子、探马架望远镜、机房冒蒸汽 | `swimlane_strip` / telemetry |
| 卡住了 | `blocked` + `blocked_question` | 那位店主走到门口举牌，一句话、二选一 | `alert_card` / `choice_pills` |
| 初审 | `auditing`（l1/l2） | 她在账房对账，可能打回重做 | `findings` |
| 交付 | `ready_to_report → done` | 交付箱"咚"一声，吐出三句话验收卡 | `spotlight_card` |
| 休息 | `idle` / ambient | 院子、书架、窗边；精力低会靠墙打瞌睡 | `energy` 三段 / presence |

### 3.3 她的"生活"从哪来——只用真实数据，不编

| 真实数据 | 世界的表现 |
| --- | --- |
| 按天日记 | 傍晚她坐在窗边写；点她能读当天那篇 |
| 心境偏置 | 走路速度、停留位置、看你的频率 |
| 精力 energy 三段 | 打哈欠、靠墙、坐在台阶上 |
| 星图记忆 | 夜空里亮起的星；镇子里的旧物（你送的那件东西一直在桌上） |
| 待办 | 睡前把明天要用的东西摆到门口 |
| presence 三态 | 灵动伴随=她在院子里；静默旁观=她在屋里；无痕闲聊=她不在画面里 |

**代价要说清楚**：这些表现需要一套"日程式"的调度（谁能出现在哪、什么时段做什么），
是这个世界里最像"游戏"、也最容易失控的部分。第一版建议只做 3 个位置、4 个时段。

## 4. 三个方向

### A. 窗中镇（推荐）

像素世界占主舞台约 65–75%，四周留纸边做入口；对话、回执、设置仍然是纸面浮层。
菜单按你说的收进边上一列（邮箱 / 告示板 / 交付箱 / 她的抽屉），主舞台不再有按钮。

- 优点：保住现在这套已经打磨三轮的排印与信息架构；中文长文本仍然可读；改动可控。
- 缺点：不算"全屏游戏"，沉浸感弱一档。
- 工作量：中。世界层可独立开发，纸层几乎不动。

### B. 全屏镇

整个窗口都是像素世界，菜单变成游戏内 UI（告示板、背包、书桌），文字用 12px 点阵。

- 优点：最沉浸，最像"她活在一个世界里"。
- 缺点：**中文可读性是硬约束**——像素中文低于 12px 基本不可读（见 §5.3）；
  信息密度骤降，"三秒法则"很难守；等于把三轮手帐设计全部推倒。
- 工作量：大。需要重做全部信息层。

### C. 双模切换

手帐 ↔ 小镇一键切换，两套视图并存，同一份状态。

- 优点：过渡平滑，随时能退回高效模式。
- 缺点：双份维护；两套交互语法会互相稀释，容易变成"两个都不好用"。
- 工作量：中大（≈A + 一套切换与状态同步）。

**建议：A，但把 A 的结构设计成能长成 B。** 世界层与纸层解耦，纸层随时可以收进抽屉——
如果 A 验证成功，B 只是把纸层再收一档，而不是重写。

## 5. 技术路线与风险

### 5.1 分辨率与图块（先定这个，它锁死后面所有美术）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 图块 | 16×16 | 与星露谷同规格，资产生态最全（OpenGameArt / itch 上 16px 素材最多） |
| 逻辑分辨率 | 480×300 | 1440×900 正好 3 倍整数放大；1920×1080 用 4 倍 |
| 角色 | 16×32 | 一宽两高，门框走廊读得对（星露谷农夫同规格） |
| 放大 | 只允许整数倍 | 非整数倍会模糊、会渗色；CSS 用 `image-rendering: pixelated` |

一屏 480×300 = 30×18.75 块。这个尺度大约是一间屋子加半个院子——正好够"看见她在干活"，又不至于要走地图。

### 5.2 渲染选型

- **不建议引 Phaser / Pixi。** 场景是静态的（一张 tilemap + 几个精灵），Canvas 2D 手写渲染器 < 500 行就够；
  引引擎会多 300KB+、多一套生命周期，还要和现有 three 的 rAF 抢调度。
- 需要时再升级：真的要做多房间、寻路、大量粒子时再引 Pixi。

### 5.3 中文字体（这是 B 方案的死穴，A 方案的关键补丁）

- 事实：**Fusion Pixel Font（缝合像素字体）**，SIL OFL 1.1，提供 8 / 10 / 12 像素三档泛中日韩点阵，
  有 woff2 产物，可直接本地化（本项目已有 `scripts/vendor_fonts.py` 的成熟做法）。
- 结论：**12px 点阵中文 ≈ 36 CSS px（3 倍放大）是舒服的；8px 汉字缺字多且难认。**
  所以像素字只用于标题、数字、英文标签、短句（≤12 字）；
  长文本——任务说明、验收卡、设置——继续走纸面的 Noto Serif SC。

### 5.4 角色怎么来：像素化 3D，而不是从零画精灵

这是这个方案最有价值的一条技术判断：**现有的 VRM + 9 个驱动可以复用。**

- 路径：把 VRM 渲进一个 48×64（或 64×96）的 `WebGLRenderTarget`，`magFilter = NearestFilter`，
  关闭抗锯齿、`setPixelRatio(1)`，再做一次调色板量化（12–16 色）+ 1px 描边，
  最后整数倍放大贴进 tilemap。
- 为什么可行：MToon 本来就是平涂少渐变，**天然适合量化**——这是别的 3D 模型羡慕不来的。
- 为什么划算：idle / emotion / gesture / lip / gaze 五个驱动一行不改，像素角色就自动会呼吸、会眨眼、会点头。
- 已知坑：①必须做像素对齐（相机 frustum 与角色位置对齐到像素网格），否则边缘会抖；
  ②12fps 更新就够（像素风的"低帧率"是风格的一部分，还能省 80% 开销）；
  ③48px 高的角色，脸只剩 12px，**表情必须靠体态和大动作，不能靠五官**——这一点要在美术定调时就认。
- 退路：如果量化后不好看，再请人按同一套骨架画 sprite，渲染层换个来源即可（接口不变）。

### 5.5 架构：世界是投影，不是真相源

```
真相源（SQLite 台账 / WS 事件 / telemetry）
        ↓  只读
投影层  project(state) → scene{ actors[], props[], lights[] }   ← 纯函数，可单测
        ↓
渲染器  render/svg（备选造型） | render/vrm（3D 图版） | render/world（像素小镇）
```

- **不加新协议、不加新表、不写新的真相源。** 第一版完全可以从现有
  `GET /api/executive/commissions` + `aqi_blocks` 的 swimlane 数据推导出来。
- `project()` 用纯函数，像现在的 `render/stage.js` 一样可以在 node 里断言——
  "这张单在 running 且 step_idx=2 → 营造匠在工坊、锤子第 2 帧" 是可测试的。

### 5.6 风险分级

**P0（不解决就不要开工）**

1. **中文可读性**：像素中文 < 12px 不可读 → 长文本必须留在纸面（铁律 4）。
2. **游戏化反噬**：任何"不维护就退化"的机制都会把人赶走（Habitica 教训）→ 铁律 1、2。
3. **效率倒退**：现在是"一眼看到进行中"，像素世界可能变成"要看动画才知道"→ 三秒法则 + 纸面随时可调出。

**P1（第一版就要有对策）**

4. **资产量爆炸**：9 个角色 × 4 个动作 × 多方向 = 上百帧。对策：先做 3 个铺子、每个 3 个动作、
   单朝向（像《星露谷》NPC 那样只做必要方向）；其余用"灯光/烟/纸页"暗示。
5. **性能**：3D 渲 2D 每帧一次离屏渲染。对策：12fps + 只在窗口可见时跑 + 复用现有单一 rAF。
6. **可访问性**：低对比、小字、纯视觉。对策：保留一套等价的列表视图（现有的工作台抽屉就是），
   键盘可达，`prefers-reduced-motion` 下停掉循环动画。

**P2（可以晚点）**

7. 移动端：小屏上像素世界信息更少，建议移动端直接退回"纸面 + 状态条"，不做镇子。
8. 审美打架：暖纸手帐（沉淀）与像素（游戏）是两种调性，必须有明确边界，不能糊在一起。
9. 长会话性能：世界持续跑 rAF 与语音播放、3D 形象同时存在时的调度。

## 6. 需要你拍板的五个问题

1. **A / B / C 选哪个？**（我推荐 A，且按"能长成 B"的结构做）
2. **第一版几个铺子？**（我建议 3 个：书桌 / 工坊 / 瞭望塔；机房先做"地下"，只出蒸汽和声音）
3. **世界时间跟真实时间，还是自成昼夜？**（我建议跟真实时间，光影按时段走，但**不做**"她睡觉了就不能派活"）
4. **第一版是纯观察，还是可以在镇子里操作？**（我建议纯观察 + 点热点打开纸面卡片；
   直接在镇子里派活会同时改交互契约和协议，风险翻倍）
5. **移动端要不要镇子？**（我建议不要，退回纸面）

## 7. 我的整体判断

- 这个方向**成立**，而且比"继续打磨立绘"有前途——因为它解决的是"多 Agent 只能在卡片里排队"这个真问题。
- 但它**不是一次 UI 改版，是一次产品形态变更**：从"一个会说话的形象"变成"一个你能看见她在干活的地方"。
  这句话应该写进产品定位，而不是只写进设计稿。
- 最大的风险从来不是像素画得好不好，而是**看世界比看任务更费神**。
  所以第一版应该把"世界"做成**可关的一层**：关掉它，产品仍然是现在这个能干活的手帐。
- 一句话（可对外复述）：**把任务面板换成一扇能看见她干活的窗——状态机一条不改，只多一个渲染器。**
