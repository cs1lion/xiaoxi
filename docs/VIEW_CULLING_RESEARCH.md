# 视野裁剪：实测与方案研究

- **状态**：**已实施并实测**（`src/render/bake.ts`）；分块与图集方案仍为备选
- **日期**：2026-10-22
- **触发**：`docs/LARGE_WORLD.md` 的「视野裁剪」待办

## 一、问题有多严重

用 CDP 抓了一次拖动时的主线程剖析（2 秒，30 次鼠标移动）：

| 函数 | 采样数 | 占比 |
|---|---:|---:|
| `GraphicsWebGLRenderer` | 801 | 约 31% |
| `batchQuad` | 523 | 约 20% |
| `(program)` | 1566 | 约 60% |

前两项加起来超过一半。渲染统计（`window.Oracle.renderStats()`）：

| 指标 | 实测 |
|---|---:|
| Graphics 对象 | 16 |
| 绘制指令总量 | **771,953** |
| 最大一个 | 511,576（地形） |
| 第二大 | 247,367（迷雾） |

换算成顶点：每帧 463 万个顶点，约 70MB 顶点数据。60fps 下是 4.2GB/s。

**而可见区域只占世界的 12.5%**（480×320 视野 / 1280×960 世界）。也就是说 87% 的
绘制工作花在了屏幕外。

### 帧率影响

| 场景 | 帧率 |
|---|---:|
| 静止 | 47.1 |
| 拖动 | 42.2 |
| 缩放后 | 46.0 |

无头 Chrome + SwiftShader 下这个数字本身不算差，但**拖动掉 5fps** 是可见的。
真机 GPU 会好很多，但问题性质不变：工作量与地图大小成正比，与视野无关。

## 二、为什么会这样

地形是一次性画进**一个** Graphics 对象的（`tilemap.ts` 的 `drawTerrain`）。
Phaser 的 Graphics 不是缓存纹理：每一帧它都会遍历 `commandBuffer`，
把每条 `fillRect` 重新三角化成 quad、重新上传。

所以地图越大，每帧的工作量越大，即使镜头没动。

## 三、候选方案

### A. 渲染到 RenderTexture（推荐）

把地形先画进一张 `RenderTexture`（或 `canvas` 纹理），之后每帧只贴一个 quad。

- **收益**：地形从 51 万条指令降到 1 条。预计总指令降到 25 万以下（迷雾仍是大头）。
- **代价**：地形变成静态纹理，扩建新楼后需要重绘一次（不是每帧）。
- **风险**：1280×960 的纹理占显存约 4.7MB，可接受。

### B. 按视野分块（Tiled）

把世界切成若干块（比如 8×8 格一块），只渲染视野内的块。

- **收益**：指令量从"全图"降到"视野 + 边缘"。
- **代价**：块边界要处理接缝；相机构造变复杂；**每块仍是一个 Graphics**，
  只是数量变少——总量与 A 差不多，但实现复杂度高得多。
- **判断**：如果 A 已经够用，B 不值得做。

### C. 地形用 TileSprite / 图集

把每种地形做成一张 16×16 的纹理，用 Phaser 的 Tilemap 或 TileSprite 铺。

- **收益**：这是引擎级的正道，批处理效率最高。
- **代价**：要把现在所有手绘的 `drawTexture`（草簇、板岩缝、垄线）都预渲染成图集。
  工作量最大，且会改变美术产出的方式。
- **判断**：当前不需要。如果将来地图到 320×240，这是唯一撑得住的路。

### D. 缩小迷雾的指令量

迷雾是第二大来源（24 万条）。它按 4px 小块铺满全图，同样与地图大小成正比。

- 迷雾也可以用 A 的同一张 RenderTexture（画在同一张静态图上）。
- 或者只在视野附近画，而不是全图。

## 四、实施结果

方案 A 已落地：地形与迷雾各烘焙成一张纹理（`src/render/bake.ts`）。

| 指标 | 实施前 | 实施后 |
|---|---:|---:|
| 每帧绘制指令 | 771,953 | **475** |
| 静止帧率 | 47.1 | **60.6** |
| 拖动帧率 | 42.2 | **60.3** |

指令量降了约 1600 倍，帧率顶到 60 上限，拖动与静止已无差别。

回归门禁：`scripts/check-render-budget.mjs`（4 项）——指令上限 3 万、
拖动帧率不低于静止的 90%。防的是「哪天又有人往大 Graphics 里塞东西」。

### 实施中的两个坑

1. **同名纹理不会更新。** `generateTexture` 遇到已存在的 key 会直接复用，
   画面停在上一版。重烘前必须先 `textures.remove(key)`。
2. **烘焙纹理不随场景销毁自动释放。** 必须在 `shutdown()` 里手动清，
   否则热更新或重进场景时会残留。

## 五、原建议

**做 A，顺带把迷雾也并入同一张纹理。**

理由：

1. 地形与迷雾都是**静态**的（地形只在扩建后变，迷雾只在揭示半径变时变）。
   把它们烘成一张纹理，是这类内容的正确做法，不是权宜之计。
2. 实测 87% 的工作在屏幕外；A 直接消掉这 87%，B 只是减少一部分。
3. C 是正道但工作量最大，而当前 80×60 用 A 已经足够；留到地图再大时再做。

### 验收标准（已全部满足）

- `renderStats().totalCommands` 从 77 万降到 **3 万以下**。
- 拖动帧率不低于静止帧率的 95%。
- 扩建一栋楼后地形正确更新（不是残留旧纹理）。
- 迷雾揭示半径变化后正确重绘。
- 既有 349 项单测与四套浏览器回归全绿。

## 六、不做什么

- 不引入新的渲染依赖。
- 不改地形的手绘画法（`drawTexture` 的草簇、板岩缝都保留，只是改画到离屏纹理）。
- 不为 80×60 做分块 LOD。当前规格用 A 够了。
