# 从一次经历到可复用做法

日期：2026-10-13。当前方向是复用已有 LLM、工具与存储，从工作经验中整理程序性记忆；不以引入 Agent 框架为前提。

实施状态：已完成[离线探针](../scripts/probe_procedural_memory.py)，13 项检查通过，生成[结果记录](../eval/research/procedural_memory_probe_20261013.json)。2026-10-14 又完成首轮真实模型试跑及独立 Codex 定性复核，见[试跑结果](PROCEDURAL_MEMORY_RESULTS_20261014.md)。三个实际归纳候选都未通过固定校验，P 组没有注入卡片，尚不能证明自动经验有收益。未接入线上聊天与后台学习，人类语义评分仍为空。

测试流程：见 [PROCEDURAL_MEMORY_EVAL.md](PROCEDURAL_MEMORY_EVAL.md)。2026-10-14 已实现默认计划、临时来源制作与显式真实模型入口，24 项离线合同测试通过。首轮真实试验使用 71 次请求，完整保留失败和空卡。机械检查、模型归纳、适用性、迁移收益和反例修订分开报告；下一步先改善归纳交付，再安排真实检索与保留任务。

归纳交付的 [V2](PROCEDURAL_MEMORY_INDUCTION_V2.md)另用了 3 次真实请求，新增 33 项离线检查通过、1 项权限相关检查跳过。输入 token 降至 17480，一张卡程序接纳但含不支持的恢复建议；见[结果](PROCEDURAL_MEMORY_INDUCTION_RESULTS_20261014.md)。下一步优先学习有证据的停止条件，尚未进入目标迁移或线上学习。

[独立输出诊断与失败教训V3](PROCEDURAL_MEMORY_DIAGNOSTICS_RESULTS_20261014.md)再用7次预定请求分开检查输出与语义，新增15项离线检查通过。新教训未编造恢复，但一项未知断言过宽：完整新正文可核对匹配，当前旧提案仍不能完成写入。程序性记忆还需准确区别信息、能力与授权边界；引用真实、JSON完整及谨慎语气都不能代替语义正确。

## 能力怎样成为记忆

可复用能力包含“下次遇到相似条件应该怎样做”。保存步骤、前提、失败教训和结果来源，是程序性记忆的一种实现。检索这些资料可以帮助模型规划，但保存了一段做法并不意味着新增了一个可调用工具、保证成功或修改了模型权重。

| 信息 | 本项目中承担的作用 |
|---|---|
| 用户事实/偏好 | 知道用户说过什么、希望怎样相处 |
| 工作经历 | 知道当时的目标、操作、失败与实际结果 |
| 可复用做法 | 提供带条件的步骤和注意事项，供当前请求参考 |
| 工具能力 | 执行已注册、经过参数/对象/权限校验的业务操作 |

程序性记忆可以改变本轮建议与工具选择。新增可执行工具则是另一项工程变更，需要独立实现、验证和注册；不能从“模型写了一段代码”直接变成已验证能力。

## 最小实现落点

现有 `NoteStore` 已支持 SQLite 保存、不可变版本、精确版本读取和删除。原型复用它保存结构化经验卡，不新增记忆数据库、向量索引或运行状态机。普通笔记正文仅充当存储载体，类型与用途由经验卡的明确字段限定。

经验卡由两部分组成：

- **经历证据**：本次目标、实际发生的操作、原稿/保存版本、观测到的结果和失败。旧对象引用属于证据，不作为下一次操作的目标。
- **做法候选**：任务家族、适用前提、需要的现有能力、步骤、失败教训和上述证据引用。原型中的候选由人工/脚本提供，尚未验证真实模型的归纳能力。

没有把程序性记忆加入普通 `MemoryStore.KINDS` 或用户事实抽取器。当前事实抽取限制来源为用户消息，不能为了记住工具经验，放松成“助手说过就算事实”。用户自述、模型提议、程序观察应继续区分。

## 本次原型的范围

以“修改已关联笔记的可见原文”为例，复用当前局部补丁与 `NoteProposalService`：读取原版、检查替换位置、生成预览、确认保存新版本，再记录可观察结果。

可归纳的做法是：

> 面对已关联、仍为当前版的保存笔记，只修改能唯一定位的原文；生成预览供核对；确认后保存新版本。不可见尾部保持，版本冲突时先停止并核对。

原型必须区分“生成了预览”和“实际保存”。保存成功只证明对应版本写入，不能证明文字更好、所有事实正确或用户满意。

一张可复用卡的内容可以像这样，字段名称以原型实际实现为准：

```text
做法：已关联笔记的局部修改
适用：已保存、当前版、原文可唯一定位
步骤：读取固定版本 → 提出局部修改 → 核对预览 → 确认保存
检查：旧版仍可读取；未展示尾部保留；新版本有实际回执
失败教训：版本变化后停止，不刷新基底重试覆盖
来源：具体经历与精确笔记版本
验证范围：领域保存与冲突边界；文字质量与通用适用性未验证
```

之后换一份笔记检索该候选。当前对象、版本、修改内容和确认必须重新建立；不重放历史参数、候选 token 或确认 token。候选只作为参考，检索不产生业务写入。

原型检索使用显式任务家族与前提匹配，证明条件过滤机制；不宣称测到了自然语言检索效果。工具/前提缺失时，不把相似文字当成适用依据。

原型 schema 包含 `record_type`（procedure/failure_lesson）、`candidate_origin`、`task_family`、`requires`、`required_capabilities`、`advice`、`evidence`、`validation_scope` 和 `grants_authorization=false`。`required_capabilities` 指向已有领域方法，不表示新增了通用 Agent 工具。

经历目录由脚本依据实际临时操作建立，证据解析到精确版本与正文摘要哈希。它不是从模型提供的 `origin=host_observation` 标签建立可信度；笔记 `source` 字段也只是自由文本标签。成功声明还须有同对象的原版/新版两个来源、版本递增和实际回读，空来源或只给一个来源被拒绝。

## 应验证的边界

1. 来源确实引用本次程序观察和精确保存版本；模型自己声称成功不构成证据。
2. 候选先保存为资料，不能因一条成功记录就升级为通用能力。
3. 预览不写笔记，确认后才有新保存版本与成果来源。
4. 新任务只使用新对象与当前版本，旧对象仅出现在经历证据中。
5. 前提或能力不匹配时不复用；匹配也只是候选资格，不证明语义适用。
6. 冲突与失败经验可以保留，但不得自动重试覆盖或把失败写成成功。
7. 经验卡版本变更保留旧版；删除后新查询不再返回已删经验。

上述检查应使用临时数据库和现有实际领域方法，不通过直接预填“保存成功”来伪造结果。实际 LLM 归纳、检索与使用质量另行评价。

## 已执行的离线验证

```powershell
.\.venv\Scripts\python.exe -X utf8 -B scripts/probe_procedural_memory.py --output eval/research/procedural_memory_probe_20261013.json
```

结果为 exit 0、13/13。它覆盖未展示尾部、预览不写入、精确新版本/旧版保留、原版冲突不重试、伪造/未执行/缺版本证据、做法卡版本修订、新对象绑定、缺前提/能力过滤、旧确认拒绝、目标版本变化、来源删除和经验卡删除。

报告含两次实际领域保存的 host episode。第二次使用独立手写改写结果、新的目标和确认 token，证明相同领域步骤可以复用；返回的 advice 本身未被解释执行。因此不能归因为“经验提高了模型表现”。

所有 SQLite 位于 `TemporaryDirectory`，结束后清理；独立加载领域模块，未启动应用或读取实际模型配置。保留下来的 JSON 报告含合成对象 ID 与摘要，是本次实验记录，不能在生产中解析或继续操作这些对象。

## 如何继续，保持复杂度有限

第一步离线机制验证已完成。第二步重新收集限定的公开目标、动作、结果与必要原文片段，用已有 LLM JSON 调用产生做法候选，与人工候选比较：有没有错误归因、遗漏前提、把一次成功过度推广、把旧参数固化成步骤。当前报告的 ID/摘要哈希不足以单独作为归纳 prompt，不能让模型据它补造过程。

只有归纳质量可接受后，再试显式的“把这次做法记下来”入口。复用已有候选预览和笔记保存界面，先形成资料；不在每轮聊天增加反思、分类与审核调用。

最后比较新任务没有经验、只有原始经历、带做法候选三组。记录任务结果、步骤/工具次数、延迟、错误对象与失败恢复。只有重用确实减少错误或步骤时，才考虑自动选择与后台归纳。

目前离线的任务家族/条件验证不能解决完整语义适用性。生产接入还需要统一记忆开关、来源删除后的失效、上下文预算，以及实际工具能力版本变化的检查；这些不能因原型通过而认定已经完成。

## 成熟做法的借鉴

本轮核验了三项作者论文与固定提交源码。它们是研究实现，效果依赖环境、模型和评估，不能当成通用生产组件。

| 实现 | 保存什么 | 借什么 | 限制 |
|---|---|---|---|
| [Voyager](https://arxiv.org/abs/2305.16291v2) | JavaScript 技能代码与文字描述 | 完成后保存可组合技能，描述用于检索 | Minecraft 环境；自动 critic 仍可能是模型判断，不等于形式验证 |
| [ExpeL](https://arxiv.org/abs/2308.10144v3) | 成功/失败轨迹、文字反思与规则 | 同任务成功/失败对照，保留可复用经验 | HotpotQA、ALFWorld、WebShop 等评估；模型归因和规则计数不是客观置信度 |
| [ACE](https://arxiv.org/html/2510.04618v3) | 带 ID 与反馈计数的文字条目 | 小条目、局部增量修改，避免反复重写整份总结 | 当前 Curator 完整支持的操作只有 ADD；条目合并也可能调用模型 |

源码依据：Voyager 的[成功后入库](https://github.com/MineDojo/Voyager/blob/55e45a880755d0c8c66ca7fb5fe7962ac8974f89/voyager/voyager.py#L353)、[代码/描述保存与检索](https://github.com/MineDojo/Voyager/blob/55e45a880755d0c8c66ca7fb5fe7962ac8974f89/voyager/agents/skill.py#L61)；ExpeL 的[成功/失败抽取](https://github.com/LeapLabTHU/ExpeL/blob/e41ec9a24823e7b560c561ab191441b56d9bcefc/agent/expel.py#L124)、[规则更新](https://github.com/LeapLabTHU/ExpeL/blob/e41ec9a24823e7b560c561ab191441b56d9bcefc/agent/expel.py#L696)；ACE 的[仅应用 ADD 的实现边界](https://github.com/ace-agent/ace/blob/82709de050e1db6e6ef2f07bcb0393560b94992a/ace/core/curator.py#L327)、[模型合并条目](https://github.com/ace-agent/ace/blob/82709de050e1db6e6ef2f07bcb0393560b94992a/ace/core/bulletpoint_analyzer.py#L193)。

当前文字经验卡优先借 ExpeL 的成功/失败分开与 ACE 的条目化观念。更新继续用项目已有不可变笔记版本与比较保存，不照搬模型自动覆盖和自评计数。Voyager 说明“技能库”可以包含可执行代码，但本轮不执行从经历中生成的代码。
