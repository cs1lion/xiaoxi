# 共同事项：决定依据、修订与跨会话接续

2026-10-14。落实[组合记忆设计](MEMORY_COMPOSITION_DESIGN.md)的第二增量代码与离线验收：共同事项保留确认请求、不可覆盖的事件版本和固定笔记引用；普通聊天与行动助手按当前问题读取相关的早期记录及历史。真实复杂任务试用、云模型语义评分和电脑外放验收尚未完成。

## 可以怎样使用

1. 在主页明确关联共同事项；需要材料时，在笔记页关联一个已保存版本。
2. 说“记个决定：周六用共享单车，因为想沿河停下来拍照”。核对候选、原请求和关联版本，确认后才保存。
3. 条件变了，提出“把共享单车改成地铁，因为周六预报有雨，沿河拍照暂缓”。核对原内容与新内容后确认更正。
4. 重新打开页面或建立新对话，仍选择同一个事项，问“为什么之前用共享单车，后来改成地铁？”系统可以提供同事项的相关当前记录及保存的历史依据。
5. 在事项页点击每条记录的“查看依据与修订”，查看完整保存版本、前版关系、请求时间、保存时间和固定笔记版本链接。再次展开会重新读取。

普通“继续这件事”仍使用简短回顾，保留下一步和小量最近记录；不会每轮朗读整段历史。简单问题不需要创建事项。

## 保存什么，怎样解释

事件 ID 保持稳定，当前文本维持原 API 行为。确认新增或更正时，当前事件更新、不可变版本追加、事项 revision 增加都在 `threads.db` 同一事务提交。`previous_version` 表示同一记录的修订关系；新决定不会因文字相似被自动推定为旧决定的替代。

| 来源状态 | 含义 |
| --- | --- |
| `user_confirmed` | 用户通过原候选卡确认了保存内容；保留最初请求全文、发起时服务器会话来源和请求时间 |
| `manual` | 明确 UI 手动添加或更正；不冒称关联了聊天原话 |
| `legacy` | 旧数据库只知道当前保存文本；原请求和既往修订未知 |
| `tool_verified` | 现有服务提供的真实工具回执，只证明对应操作结果 |

**确认请求不是决定全文的逐字证明。** 模型可以归纳，用户也可以编辑候选；“把刚才那个记下来”只证明这是当时的请求，不能独自解释“刚才那个”的完整依据。没有把截短聊天拼成逐字证据，也没有伪造聊天消息 ID。本轮保存本地请求快照，尚未建立事项到聊天消息表的完整引用链。

主页对话提出的候选固定目标事项、来源会话、请求时间和当时明确选定的笔记 `id + version`。等待模型、编辑候选或确认前切换选择，都不会换成后来选择的对象；澄清续接保留原资料引用。更新预览只修改候选内容与明确重读的同目标比较版本，不重置原请求时间。独立事项页的严格候选接口保留该页输入与请求时间，没有聊天会话来源，也不自动绑定全局笔记选择。

笔记引用表示“当时关联的保存资料”，不证明笔记支持结论，也不推断全局笔记选择属于某个项目。预览中先显示引用，确认后与对应事件版本一起保存；不复制笔记正文。新的笔记保存回执也增加结构化固定引用，沿用实际返回的新版本，不把整个事项标为完成。

手动更正追加新版本，并清除当前版原有的请求依据和资料引用，避免新文字冒用旧依据；旧版仍保留其原始关联。下一步、标题、事项状态仍沿用当前值更新，本轮没有给它们新增完整历史链。

旧库采用增量建表：只把已有最后保存文本保存为 v1/legacy，时间沿用已有 `updated_at`，不重建不存在的旧文本或原话。新版本的保存时间是确认/手动保存时间，原请求时间另列。旧行 `created_at` 继续表示事件最初创建时间。

## 怎样找回早期依据

`Participation` 同时用于普通聊天的 ContextBroker、行动上下文和只读 `thread.read`。查询只在明确选择或明确 ID 指定的事项内进行；当前事件按中文双字与英文完整词进行词法匹配，结合最近事件，最多 12 条。没有新增向量调用或图数据库。

询问“依据、原话、为什么、以前、怎样改”等问题时，才扫描该事项的保存历史。历史中的旧关键词也可召回已改写的记录；最多展开 3 条相关事件，每条最多 4 个保存版本，保留最初版与当前版，中间版按问题相关度选择，并报告省略数量。当前记录与 `event_histories` 分开，历史版本有 `is_current` 标记；词法未命中时不编造理由。

单份视图包含边界说明的紧凑 JSON 上限为 8000 字符。完整检查凭据、异常来源与时间；不把内部 session ID 交给模型。预算不足时省略整条记录或整版，不裁掉末尾否定、条件或时间限定；历史全因预算省略时标明 `budget_omitted`。`thread.read` 直接沿用这份有预算的视图，不再二次按 1200 字截短事件文本。它是事项域预算，不代表整轮所有领域上下文已有统一预算。

澄清时展示的事件集合和编号固定到同会话；下一句“第一个改成…”只允许对应实际展示的 ID。早期召回不会在保存澄清状态时又被尾部 12 条替换。确认继续沿用事项 revision 与候选 version 比较，冲突不自动重试。

## 管理与生命周期

- 新增 `GET /api/threads/{thread_id}/events/{event_id}/history`，返回升序 `items`，成功响应 `Cache-Control: no-store`；跨事项、缺失或删除 ID 返回 404。
- 客户端写接口继续禁止传入 evidence、source、object_refs 等来源字段；来源与笔记引用由服务端捕获，确认前没有写入事件版本。
- 每事项最多 200 条事件，每事件最多 200 个版本；达到上限拒绝继续写入，保留已有历史。笔记引用每版最多 6 个，当前只实现 note 类型。
- 删除事项同事务清除当前事件、全部版本和关联选择，保留无正文 ID 墓碑；迟到候选不能复活。事项页清除已隐藏的历史 DOM。
- 删除笔记会使对应保存版不能再打开；事项历史仅留下固定 ID/版本，不恢复或复制已删正文。当前没有跨域遗忘传播，删除事项也不删除原聊天、任务、笔记或备份。
- 关闭记忆时，不为新候选读取笔记引用、不展开模型历史或调用语义解析。显式 UI 编辑、严格记录命令和确定性的直接回顾沿用原行为。
- 用户明确打开事项页的历史是本地管理操作，不受模型记忆开关限制；页面不展示内部来源会话 ID。

历史扫描受上述事件与版本数量约束。本轮没有长期容量或 p95 性能基线；读取已开始的快照不能撤回已经发送给模型的内容。普通事件快照不等于整个事项 revision 的可重读快照，`ObjectRef(type=thread)` 仍只是当前事项的版本标签。
