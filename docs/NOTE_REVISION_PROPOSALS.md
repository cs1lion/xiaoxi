# 从已保存原稿到可确认的新版本

2026-10-13 实施记录。主聊天现在能对明确关联的已保存笔记提出修改，展示原稿、新稿与差异；用户确认后才写入一个新保存版本。

2026-10-14 更新：[事项资料用途与范围](SHARED_THREAD_MATERIALS.md)已接入。选定事项后只修改其唯一当前稿；未选事项时沿用下面的个人笔记关联流程。候选显示原归属，来源解除/换版/改用途后拒绝继续读取或确认，草稿可保留或拒绝。事项候选保存后需在原事项资料中明确更新固定版本，没有个人关联按钮。

## 使用流程

1. 在笔记页打开已保存的当前版，点击「关联之后的对话」。
2. 回到聊天，说「修改这份笔记，把第二段写得具体一点」等明确修改请求。
3. 核对候选中的原稿、新稿与差异。需要时编辑候选标题、正文，再点击「更新预览」。
4. 点击「确认保存新版本」。不采用建议时点击「不保存」。
5. 保存回执可打开精确版本。想让后续对话使用它，再点击「关联此保存版本」。

保存 v2 后原关联仍是 v1。明确关联是独立操作；另一窗口改变关联时返回冲突，不自动覆盖。候选卡不会重载笔记编辑器，编辑器内未保存的输入仍保留。

## 原稿与修改的约束

候选固定最初的 `note_id + base_note_version`，事项内同时捕获原事项及材料 ID；个人流程不自动捕获共同事项 ID。生成中更换笔记或事项不会改变候选归属。关联旧版时先要求核对并明确关联当前版；已有行动的澄清或确认始终优先。

模型看到正文前 4000 字及最多 6 条短历史，只返回最多 8 个局部替换或明确标题修改。替换原文必须在可见正文和完整原稿中均唯一，且各处不重叠。本地将补丁应用到完整的不可变快照，未展示的尾部完整保留。模糊、重复、不可见位置、无变化或不合格式的结果进入澄清，不生成可保存候选。

全原稿先检测凭据内容；不能依据已过滤的原文生成保存建议。关闭记忆时，在读取关联、正文或调用模型之前结束这条流程。普通解释、总结、整理与起草继续沿用已有入口。

无需模型的精确替换入口为 `笔记替换：「原文」→「新文」`，仍必须审阅并确认；原文同样需要唯一。

## 保存、冲突和成果回执

候选仅存在当前进程内，最多 128 个，10 分钟过期，重启后不保留。候选修订号和原稿保存版本均进行比较更新。候选修订冲突可读取最新预览后重新核对；原稿已有新版时，旧候选不能刷新原稿或继续保存，须核对并明确关联新版后重新生成。页面保留候选编辑草稿，不自动重试写入。

确认保存先在 `notes.db` 写入一个新版本并消费候选，再向最初共同事项追加 `tool_verified` 成果回执，引用实际保存的 `{type: note, id, version}`。不会把整个事项标成完成，也不会移到后来选中的事项。

这是跨数据库的先保存、再关联，不保证跨库原子提交。原事项已删除、变化或回执同步失败时，笔记仍已保存，页面显示警告；不得因此重复保存。删除笔记立即清除其候选缓存和保存历史。

## 接口与验证

| 接口 | 行为 |
|---|---|
| `GET /api/notes/{id}/proposals` | 当前待审候选列表 |
| `GET /api/note-proposals/{id}` | 固定原稿与候选预览 |
| `PATCH /api/note-proposals/{id}` | `{expected_version, title, body}` 修订候选，不写笔记 |
| `POST /api/note-proposals/{id}/confirm` | `{expected_version}` 确认一次保存 |
| `POST /api/note-proposals/{id}/reject` | `{expected_version}` 放弃候选 |

接口限制字段并检查同源，成功读取使用 `Cache-Control: no-store`。缺失、过期、删除或已消费返回 404；候选或原稿版本冲突返回 409。

隔离验证使用临时 SQLite、注入解析结果和假的音频边界。新链路覆盖候选生命周期、真实 API 确认、删除、固定版本接续、选择竞争、长稿尾部、凭据、记忆关闭、WebSocket 有声交付与取消。浏览器检查差异、候选编辑、两类冲突、关联新版和回执失败，以及原助手、共同事项和主页回归。

没有在用户数据库生成验收笔记或事项，没有调用付费模型或生成收费音频。这些结果证明保存和交付边界；真实云模型的自然语言定位与改写质量仍待实际使用验证。声音继续采用已选定的自然语气。
