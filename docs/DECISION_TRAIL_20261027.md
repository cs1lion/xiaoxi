## 二、卸载判据（第十六批定型，后续各批沿用）

**写事务一律卸，有界索引读留同步。**

- 写 = `BEGIN IMMEDIATE` + commit，默认 `synchronous=FULL` 每次 fsync。实测家族成本 4-18ms/次（第十六批：单行 UPDATE median 3.97ms、upsert median 9.82ms、accept worst 9.42ms；第二十三批：usage sweep 200 行批量 worst 37.86ms）。
- 读 = 不脏页、commit 近乎零成本，实测 0.07-0.5ms。`to_thread` 调度开销本身 0.248ms，卸亚毫秒读是净亏。
- 无界增长读（O(表长)）按写对待：`store.count()` 1000 行 0.34ms / 5000 行 2.16ms，history_of 全表扫描，均卸。

**不为不可达场景加机器**（Laziness Protocol）：并发来自默认执行器 worker，但快环真实并发 1-2 连接；8 线程混合读写不是生产形态，故不拆存储层单 RLock（第二十五批实测并行比 0.13 也不拆）。

## 四、三个方法论沉淀

1. **受控 A/B 分离环境漂移**。跨天比延迟数字等于把环境和代码混在一个量里。第二十六批用 `git worktree add` 到会话前父提交做同时段同机器对照，证明卸载批次对首字延迟零影响（会话前 109.8ms vs 卸载后 108.4-108.8ms），与 2026-10-24 基线的 +13ms 全归环境漂移。worktree 用完即 `git worktree remove --force`。
2. **探针必须打点验证测的是真路径**。本会话三次踩坑：第十四批探针文本被正则提前截断，量的不是目标分支；第二十八批 settle_pending 探针用同一条消息当 current，行不够结算条件，量到的是读路径；第二十三批 epiphany 边为空使一处卸载不可达。「不修」的结论比「修」的结论更需要这个证明——一个量错分支的探针能把误判伪证成数据。
3. **「保留同步」的代价不只是它自己的读耗时**。store 单连接 + 单 RLock，轻读会排在已卸载的写后面等锁（第二十五批实测混合负载读中位数被写抬到 18-33ms）。判轻路由要在「读耗时 + 等锁时长」上算，不是单机空载数字。
4. **判据本身要先被验证，别拿字面印象当判据**。本会话有五次「判据被实测推翻」：冷重建成本门禁的三个判据全证伪（绝对毫秒随机器漂移、冷热比值被同比例变化免疫、规模比被固定基数稀释）；「检索层不变量无覆盖」被穷尽检索推翻（`test_memory_retrieval.py` 早有四个专用用例）；「有 `skipUnless` 就不能登记门禁」被推翻（判据实现是「输出有行首 SKIP」，`OK (skipped=N)` 不命中）；fastloop 两处绝对毫秒阈值假红；fastloop [6] 段的增量判据恒为负。五次同源：**拿规则的字面印象当判据，没读判据的实现**。读实现的成本远低于反复证伪的成本。
5. **恒绿的判据比会假红的判据更危险**。假红吵一次就有人去修；恒绿给人确定的信心，而被测性质其实从未被检验。fastloop [6] 段的增量判据「带/不带 40ms 延迟的停顿差 < 15ms」实测 5 次全为负（-21.87 至 -40.92ms）——注入的阻塞延迟反而「改善」了测量值，因为 `to_thread` 让出循环后心跳更密。它已经这样绿了很久。检出这类问题要**定期看判据的实际输出值**，不只问 pass/fail：一个恒为 -25ms 的「差 < 15ms」和一个恒为 +2ms 的，安全性完全不同。
6. **plumbing 提交后必须逐项验证**。第五十四批用临时索引 + `commit-tree` 落库时，`write-tree` 那次调用漏传 `GIT_INDEX_FILE`，读到被并发 session 污染的主索引，把他们的 12 个文件（2970 insertions）一起提交。`git update-ref` 回退到父提交后重做。plain commit 会明明白白提交整个暂存区（所以一直警惕），plumbing 里一个环境变量漏传会让「我以为只提交了 X」变成「实际提交了 X+Y」且提交前无任何提示。
7. **共享工作区里没有任何 git 信号能区分「谁改的」，只能声明**。第六十一批想给「勿卷入他人文件」建自动检查，两种判据都实测失败：「工作区有未提交改动」会把别人的在途改动算成你的（实测把并发 session 在途的 `run_evals.py` 判成自己的，报干净 exit=0——假阴性比误报更坏）；「本会话提交碰过的路径」也会把别人的提交算成你的（他们用同一本地分支，提交同样落在 `origin/master..HEAD`）。结论是能判定的只有意图，而意图只能由提交者声明。`scripts/check_staged_scope.py` 因此收窄为「暂存区 ⊆ 我声明要提交的路径」，并写进派单宪章的完工标准。工具建立后的第一批就抓到真实污染（并发 session 暂存了删除，准备撤掉自己此前的提交）。
8. **提交信息含反引号或 `$` 时一律走 `-F` 文件**。第六十四批用 `git commit -m` 传含 `` `--allow-skip` `` 的信息，shell 把反引号当命令替换，两处参数名被吃成空档、还打出 `command not found`。文件改动完好，但提交信息残缺，靠 `--amend -F` 修正。改动可以 amend，信息残缺却可能已经在推送后没人发现。

**「既有失败」这个标签本身会掩盖真问题**：每次全量看到红就归类为老问题、不再看为什么。四个审下来三个是判据或注入问题——若继续挂着标签，`self_evolution_send` 那 4 个 FAIL 会被永远当成环境噪音，而它们其实在保护一条真实路径（协议 §十 的 self_evolution 事件发送）。

**`run_gates_verdict`**（指向 `scripts/test_run_gates.py`）：钉住 `run_gates` 的完整裁决表。真实门禁覆盖不到这条——`ui_nav_browser` 只在 8000 未起时 SKIP，8000 运行时判 PASS，即「打印 SKIP 行却 exit≠0 必须判 FAIL」这条 R51 本体在真实门禁里根本跑不到。用合成门禁钉四条腿（exit≠0+SKIP行→FAIL、exit≠0无SKIP→FAIL、exit=0+SKIP→SKIP、exit=0无SKIP→PASS）加 `--allow-skip` 不得洗绿真实失败这条边界。第三条腿容易漏：把「环境不满足、没跑」误判成 FAIL 同样危险，会让一条本该跳过的门禁把整套报告染红，训练人忽略红色。

**这段资产换过一次手，教训比结论值钱**：第六十四批我自己建了 `test_gate_verdict_r51.py`（173 行）钉同一件事，第六十六批逐条比对后发现并发 session 的 `aa9c633` 里已有 `test_run_gates.py`（97 行标准 unittest）测同一件事且覆盖更严（他们的 `:61` 多断言「不打印全绿结论」、`:78` 多断言「跳过仍让整体 exit 1」），遂删我的、改登记他们的。**成因是立项时没先搜是否已有资产**——两份资产的 docstring 里写着同一个 2026-10-27 合成门禁实证，信息就在手边。立项「补覆盖」类任务前，先搜一遍同名/同主题测试文件。

**`check_staged_scope.py`**（第六十一批，工具本身刻意**不**进 GATES）：共享仓库里 `git add <我的文件> && git commit` 不等于只提交我的文件——`git commit` 提交的是整个索引。本会话这个形态重复了至少 8 次。脚本把「提交前核对范围」从一句纪律变成一个退出码（暂存区 ⊆ 声明路径）。工具不进门禁的理由：它是开发时工具，依赖暂存区状态，在门禁子进程里跑没有意义；`scripts/` 下四个 `check_*.py` 先例也都没进。它的位置是派单宪章的完工标准（第六十二批写入）。工具建立后的第一批就抓到真实污染。

**但它的回归测试进门禁了**（第七十六批，`test_check_staged_scope.py`，4 用例）：工具不进套件，护住工具的测试要进。测试在临时目录 `git init` 造场景、不碰真实 index（为此给 `git()`/`staged_paths()` 加了可选 `root` 参数，默认仍 ROOT，生产调用不受影响）。四种形态：空暂存区 exit 0、全在声明内 exit 0、有声明外文件 exit 1 且点名+撤出命令、无参数 exit 2。判别力已验证：把 `foreign` 退化成 `[]`（什么都不拦），测试立刻抓到。

**`check_probe.py`**（第六十九批，工具本身同样**不**进 GATES）：一个探针说「绿」，你无法区分「被测性质成立」和「探针根本没在测」——除非先证明它红过。本会话「探针/判据无效」类事故出现 23 次，是最高频失败形态：等价改动（去掉 `is_absolute()`、把 `all(...)` 换成 `True`，破坏版照样全绿，曾据此误判「helper 没被共用」差点删掉正确重构）、量错路径（探针量的不是目标分支，「不修」的结论比「修」的更容易被伪证成数据）、锚点撞多处（注入脚本的锚点出现两次，`replace` 改错地方）。共同根因是**验证工具本身没被验证**。工具不进门禁的理由同上：它依赖探针上下文，在门禁子进程里跑没有意义。

**它的回归测试也进门禁了**（第七十五批，`test_check_probe.py`，7 用例，0.05s）：护住工具的测试要进。五种形态固化成常驻断言——正常注入判有效、等价改动判无效、`break_it` 空转点名「注入没生效」、还原不干净点名「还原不干净」、锚点撞多处当场炸，外加 `patch_file` 两个契约（二进制往返保 CRLF、不许返回前就注入）。目标文件用临时目录的 CRLF 文件，不碰仓库真实文件。判别力已验证：把两处 `watch` 校验退化成 `if False and ...`，测试立刻抓到 2 个失败。

两个元检查工具至此都拿到同一条待遇：**工具本身不进套件（它是开发时工具），护住工具的测试进套件（判据不许退化）**。

工具建成后**又演进了三次，每次都是被真实事故逼出来的**（这比初版设计更值钱）：

- **第七十一批**：`patch_file` 从 text 模式改二进制读写。原因是用它审计四个 CRLF 门禁后 `git status` 显示 4 个 M——内容逐字节一致但行尾被改写，只能 `git checkout` 归位。教训是「还原后退出码为 0」不等于「还原干净」。
- **第七十二批**：`probe_self_check` 加 `watch` 参数，把「逐字节还原」编进判据（此前只写在 docstring 里）；`patch_file` 同时改成返回 `(inject, restore)` 且不立即注入。后者是这次自己踩的——返回前就注入会让 `break_it` 前的快照拍到破坏版，误报「还原不干净」，而同一行打印的「逐字节还原: True」当场戳穿了矛盾。
- **第七十四批**：加「`break_it` 之后文件必须与注入前不同」判据。第七十三批踩的坑：API 改成返回 `(inject, restore)` 后，调用点仍写 `break_it=lambda: None`，inject 从未被调用，文件纹丝未动，三个门禁全绿，被误判成「恒绿（判据无效）」——那不是等价改动，是什么都没测。

四条判据的分工：等价改动/只抹一处由 `break_exit == 0` 判「探针无效」；锚点撞多处由 `patch_file` 的 `assert count==1` 当场炸；注入没生效与还原不干净由 `watch` 的两次 sha256 比对分别把守（`break_it` 后一次、`restore` 后一次）。

**一个反复出现的形态值得单独记**：这个工具自己的文档不同步了四次（`check_probe.py` 的 docstring、宪章示例、审计文档示例、判据说明），每次都是代码改了文档没跟上。按本会话的 Encode Lessons in Structure，这类「改了 A 要同步 B」的关系要么编码成检查，要么承认它是需要人记得的步骤——此处选了后者（三处文档的 API 引用已核对一致，且变更频率低，建签名校验机制属于 gold-plating）。

## 七、共享工作区纪律（本会话的实操约定）

与并发 session 同库工作期间形成：提交前 `git diff HEAD -- <file>` 确认只带自己的 hunk；共享文件用 blob 手术（`git show HEAD:file` → 改 → `hash-object -w --no-filters` → `update-index --cacheinfo`）；手术脚本后绝不补 `git add` 同一文件（会覆盖手术成果，第九批踩过）；索引被并发暂存污染时用临时索引 + `commit-tree` + `update-ref` 落库，再同步自己路径的索引条目。
