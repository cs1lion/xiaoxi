# 下一步：减少判断与重复编排

2026-10-13。研究建议，未修改产品代码或调用实际模型。

后续推进：用户认可“归纳成可复用能力也是记忆的一部分”。当前沿此方向研究与验证程序性记忆，复用现有版本化笔记与真实结果来源，见 [PROCEDURAL_MEMORY_EXPERIMENT.md](PROCEDURAL_MEMORY_EXPERIMENT.md)。

用户所说的“成熟 Agent”是比喻：希望借用成熟做法，避免为每个自然语言功能重新造轮子。没有要求引入 Agent 框架。我们前面的 SDK 采用研究过早收窄了方向；目前不执行该方案。

## 当前建议

先利用普通 LLM 调用、已有严格工具校验和领域执行服务，找出一个真实失败点，再做可删除旧分支的小改动。引入更多运行时不会自动解决语义判断；首先要查明错误发生在入口路由、模型理解、证据、参数、保存还是交付。

降低复杂度有两条可以并用的路线：

| 路线 | 怎么做 | 适用情况 |
|---|---|---|
| 减少需要猜测的信息 | 把已选对象、精确保存版本、用户当前请求和工具真实结果直接交给模型；缺失时澄清；不从长期画像推测本次目标 | 当前对象、进度、权限、当前偏好不应依赖自由推断 |
| 收敛重复的语义编排 | 普通 LLM 输出结构化候选；复用已有 handler、补丁校验和执行服务；逐步合并重复的路由与澄清生命周期 | 每加一项能力都会增加一套正则、resolver、session 和回执协议 |

常规的局部改写可以只是一次 LLM 调用与一个预览。确实需要搜索、读取、再规划时，才进入已有工具循环。不要要求每个请求都跑多步，也不要把所有意图识别合并成一个无法定位错误的大提示词。

## 为什么项目已有基础足够开始

`server/assistant/loop.py` 已有模型决策、工具 schema、严格参数校验、澄清续答、持久确认、步骤预算与真实回执。`server/assistant/service.py` 已有领域工具注册和上下文组装；不缺一个新的运行时才能开始改进。

笔记修改已有 `NoteConversation` → 局部替换校验 → `NoteProposalService` → 审阅/保存的完整路径。通用工具暂时只有 `note.search/read`，不能宣称现有通用循环已能编辑笔记。下一步如果确认瓶颈是语义入口，可让已有笔记候选服务通过薄接口被复用，而非重写笔记编辑器或保存机制。

笔记当前有自己的进程内澄清 session，通用工具运行另有 SQLite `waiting_input`。这是可能收敛的重复状态，不能直接删除：二者的对象绑定、候选过期、确认界面和取消语义不同。先证明某个入口替换可行，再合并生命周期。

`server/llm.py` 当前只有文本/JSON 返回，没有原生工具协议。可以先沿用已有 JSON 决策与本地校验。只有故障记录显示协议解析是主要瓶颈时，再单独比较原生 tools/structured outputs；它们约束输出结构，不能证明用户意图或语义结论正确。

## 用程序消除能消除的判断

| 问题 | 已有或应复用的依据 | 剩下的模型任务 |
|---|---|---|
| “这份笔记”是哪一份 | 捕获的 note ID 与保存版本；没有依据时询问 | 理解用户想怎样改 |
| 改写是否破坏原稿 | 唯一局部替换、完整原稿应用、保尾和版本比较保存 | 提出合适的新文字 |
| 操作是否获准 | 具体参数的确认绑定、有效期和一次消费 | 提议操作；不能自授权限 |
| 是否保存或执行成功 | 实际业务写入与工具回执 | 根据真实状态表达结果 |
| 偏好是否适用本轮 | 明确范围与当前用户要求；推测不自动升格 | 在给定约束下组织答案 |
| 用户是否在引用/假设 | 原始请求、消息角色与来源；含糊时澄清 | 仍是语义任务，需要实际样本检验 |

这些做法减少必须由模型猜对的事项，并没有保证剩余语义判断绝对准确。证据片段存在不等于归纳含义正确；工具成功也只证明工具的具体效果。

## 最小下一步

1. **选择一个问题，保留当前基线。** 首选审查“修改当前笔记”的自然语言入口：是否因缺少关键词没有进入正确路径，还是进入后模型无法定位改写。不要同时调整路由、模型、记忆、保存和语音。
2. **复用原始请求和现有评价记录。** 测直接请求、改写表达、引用、取消、未选对象、版本竞争与失败回执。现有笔记/行动隔离测试继续验证领域边界；它们不能代替实际模型的理解评价。
3. **只改变语义入口做对照。** 两边使用同一模型、上下文和候选服务；可以比较当前规则入口与一个结构化语义入口。候选只是确定应答/澄清/提议，并不直接写库。保留的专属路径与真正被替换的部分分开统计。
4. **依据结果决定删什么。** 只有新入口对自然表达有收益、引用/取消不退化，且能删除重复判断/状态，才扩大。若错误来自缺证据或上下文，先修资料交付；若来自模型能力，单独比较模型，不以增加编排层应对。

先用现有 JSON 候选和严格校验就能实验，无需先安装 SDK。无需给每个请求再加一个“判断模型”和一个“审核模型”；增加调用应有错误样本证明必要。

## 借成熟做法，而不是先搬整个平台

- **工具 schema、候选/执行分离、真实回执**：本项目已有，优先整理成可复用契约。PydanticAI/LangGraph 的研究可用于核对暂停和取消语义，无须把框架引入项目。
- **按失败环节评价**：借鉴 [LongMemEval](https://arxiv.org/abs/2410.10813) 与已有 [MEMORY_RESEARCH_NEXT.md](MEMORY_RESEARCH_NEXT.md)，分别记录抽取、检索、读取、使用和未知弃答；避免把不同错误归为“模型不够聪明”。
- **时间、来源、版本**：借鉴 [Zep](https://arxiv.org/abs/2501.13956)/[Graphiti](https://github.com/getzep/graphiti) 的数据观念，使用已有 SQLite 与对象版本逐项补足；不要求先建图数据库。

已有 16 案例规格为 [agent_adoption_cases.json](../eval/agent_adoption_cases.json)，现改为决策与领域契约的待筛选题库；不是决定接入 Agent 的承诺，也没有执行结果。实际试验只选与所改接缝相关的案例，其余作为回归/能力缺口审查，不将未触及的功能计作新方案收益。

成功标准是：用户能用自然语言完成目标，错误可定位，既有数据/确认/版本边界可靠，需要维护的重复逻辑与状态确实减少。当前范围只做研究和方案，不实施迁移、安装依赖或线上改动。
