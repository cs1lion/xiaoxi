# 造物主：现状与设计文档的差距

- **状态**：调研，未实施
- **日期**：2026-10-22
- **对照**：`docs/PIXEL_WORLD_ARCHITECTURE.md` §4（四层结构）、`ADR_CREATION_MODE.md`
- **一句话**：L0/L1/L2 都在，**L3（生成器）完全缺失**；文档里另有四处已过时。

## 一、四层逐层对照

| 层 | 设计文档说 | 现状 | 差距 |
|---|---|---|---|
| **L0 世界规格** | 网格 16px、480×300、调色板上限、区域与槽位表 | `LARGE_WORLD_SPEC` 80×60、`TILE_PX` 16、24 色冻结、13 个分区 | **有**。文档的 480×300 已过时（实际 480×320 画布、1280×960 世界） |
| **L1 房间模板** | 院落/工坊/机房/街道/神殿，**各带槽位图** | `prefabs.json` 7 个模板，字段：footprint / door / workSpots / chimney / accent / silhouette / palette | **部分**。模板有，**没有槽位图**（slots） |
| **L2 组件库** | 语义化素材 `desk / forge / crate / lamp / puddle / banner`，带尺寸与锚点 | 全部手绘 Graphics，没有独立素材库；摆件三种（lamp/tree/banner），神迹三种 | **部分**。视觉组件散在各个 renderer 里，不是可复用的语义库 |
| **L3 生成器** | LLM 输出「模板 + 槽位 + 配色 + 天气」的 JSON，经校验器、缓存、实例化 | **没有** | **缺** |

## 二、L3 缺失的具体表现

设计文档的管道是：

```
LLM 出 JSON → 校验器 → 缓存 → 运行时实例化 → 落进世界记忆
```

现在实际只有中间两段的**雏形**：

| 环节 | 现状 |
|---|---|
| JSON 形状 | 无。没有定义过造物主输出的 schema |
| 校验器 | `parseBlueprint` 校验的是**蓝图注册表**，不是 LLM 输出 |
| 缓存 | 无 |
| 实例化 | `placeBlueprint` 能做，但输入是 prefabId + 位置，不是场景描述 |
| 落进记忆 | 摆件有来源，**建筑没有**（建出来的楼不知道自己为什么在那儿） |

## 三、四处文档过时

写代码前应当以代码为准，这几处需要更新文档：

1. **`480×300`** → 画布 480×320，世界 1280×960。
2. **神谕 op 名字对不上**。文档写 `set_weather / set_time / place_object / summon_actor / open_area / dispatch`；
   代码里是 `dispatch / complete / cancelPending / setWeather / build / miracle`。
   其中 `set_time` 没有对应实现（时相是纯渲染，不进世界命令），`summon_actor` 与 `open_area`
   合并成了 `miracle` 与 `build`。
3. **「可撤销：最近一条结构类 op 允许收回」** → 未实现。现在只能撤销**排队中的神谕**
   （`cancelPending`），已建成的楼不能拆。
4. **「神谕是显式模式，不是每句话」** → 实现上 `parseOracle` 是关键词匹配，
   任何含「写」「查」的句子都会被当成派活。文档要求的三条纪律只做到一半。

## 四、值得先做的两件事

按「投入产出比」排，不是按文档章节顺序：

### 1. 给建筑加来源（**已落地**）

摆件已经记着自己从哪一单来（`sourceTaskKind` / `sourceSummary`）。建筑原本没有，
一栋建出来的楼过两天就没人知道它为什么在那儿。

已做：`PlacedBuilding` 加 `sourceTaskId` / `sourceSummary`，造物模式建楼时写进去
（`在 (33,16) 建了新工坊`），日报写成「新工坊（在 (33,16) 建了新工坊）」。
存档 v2 加两条路径（114 条，指纹 `72c4a6c0f1f444f7`）。

### 2. 定义造物主的 JSON schema（**已落地**）

见 `docs/CREATOR_SCHEMA.md`，实现在 `src/world/creator-schema.ts`，
测试 19 项。

实际形状是 `{ templateId, at, palette }`，**不是**设计文档写的
`{ templateId, slots, palette, weather }`：

- 没有 `slots`：世界没有家具层，定义了也没东西能填；
- 没有 `weather`：天气是世界法则，不是造物的一部分。

这两处偏离都写进了 schema 文档，附理由。

## 五、不建议现在做的

**接 LLM 生成**。理由不是「难」，是**没有输入**：造物主该看什么来决定「这周该长什么样」？
现在的世界没有「周」的概念（四刻是时钟不是周期），也没有「神谕说想要什么」的结构化输入。
在没有依据的情况下接 LLM，只会得到随机建筑。

设计文档说「输入：这周该长什么样 / 神谕说了什么」——这两个输入都还不存在。

## 六、结论

- **L0 完备**，L1/L2 部分完备，**L3 缺失**。
- 文档过时四处，其中「神谕 op 名字」与「可撤销」最容易误导后来者。
- 先做「建筑来源」（闭合记忆线）与「JSON schema + 校验器」（为 L3 铺路），
  不建议现在接 LLM。
