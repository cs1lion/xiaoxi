## 1. P0 · 画布固定 962px，窄视口两端被裁

**复现**：打开页面 → 开发者工具切到 390×844（或 768×1024，或浏览器 200%/400% 缩放）→ 观察世界画面左右两端缺失、出现横向滚动条。

**实测**（`part1_viewports` / `part5_overflow`）：

| 视口 | `document.scrollWidth` | `clientWidth` | 溢出 | canvas `rect.left` | 左侧被裁 | 右侧被裁 |
|---|---|---:|---:|---:|---:|---:|
| 390×844 | 668 | 375 | **+278px** | **−292.44** | **292.44px** | 277.56px |
| 768×1024 | 857 | 753 | **+89px** | **−103.56** | **103.56px** | 88.44px |
| 1440×900 | 1425 | 1425 | −15（滚动条预留） | 232.44 | 0 | 0 |

canvas 固定 `rect.width = 960`（`#app` 961.78 = 960 + 2×0.889px 边框）。阈值：**视口 < 994px 即开始裁切**。

根因链（全部可定位）：

1. `src/main.ts:37-41` — `Phaser.Scale.NONE` + `zoom: 2`，Phaser 在 NONE 模式把 `style.width` 写成 `480×2 = 960px`（已核 `phaser.js:195723`）。
2. `src/world/setup.ts:12-14` — `TILE_PX=16`、`GRID_WIDTH=30`、`GRID_HEIGHT=20` → 逻辑 480×320。
3. `index.html:20-31` — `body { display:flex; align-items:center }`，越界子项**两端对称溢出**，所以左侧负左边距不可滚动到达。
4. `index.html:35` — `#stage { width: fit-content }` **缺 `max-width: 100%`**。同页 `#status`/`.oracle`/`#paper` 都有 `max-width: 100%`（`index.html:102/70/122`），只有承载画布的 `#stage` 漏了。

**期望 vs 实际**：期望窄视口下画布完整可见（可整体缩小）；实际左侧 292px 永久不可达（约 **30.5% 的世界宽度**，30 格中约 9.1 格看不见）。

**改法建议**（三选一，按侵入性排序）：

- **A｜最小改动（推荐先做）**：给 `#stage` 加视觉缩放。`index.html:35` 改
  `#stage { position: relative; line-height: 0; width: fit-content; max-width: 100%; }`
  再配 `#app { transform-origin: top left; }`，用一个 CSS 变量按容器宽驱动 `scale()`。
  注意：`world-overlay.ts` 已支持被 transform 缩放的 stage（`rootScale` 折算，`world-overlay.ts:66-73`），所以 overlay 不会脱节——这条已被 100/200/400% 实测印证（`delta` 0.215/0.146px，§3）。
- **B｜世界层解决**：`main.ts:37-41` 把 `zoom: 2` 改为按 `window.innerWidth / 480` 计算并向下取整到 1 或 2，窄视口用 1 倍。**代价**：1 倍下 16px 瓦片在 390px 屏上过小，可读性下降。
- **C｜布局层解决**：`index.html:35` 外套一层 `overflow-x: auto` 的滚动容器，承认需要横向滚动。**代价**：手机用户要横滑看世界，且左侧 292px 仍需手动滑到，体验差。

**是否触及 16 色预算**：否。A/B/C 都是布局/缩放，无新色。

## 3. overlay 与 canvas 的尺度咬合（**已修 bug，现为 PASS**）

> **本节结论已按 `32141df` 更新。** 下表 round-01 的 `delta 0.215/0.146` 与 `rootScale 0.999769` **不是「设计使然」，而是 bug 的读数**——详见 §10.1。修复后三档偏差降到 ≤0.014px。原写「这条做得对，勿改」已不成立。

**实测**（`part2_zoom[].overlayFit`，**修复前**）：

| 缩放 | canvas rect | overlay rect | `delta` (w/h/l/t) | `rootScale` | 标签锚点误差 |
|---|---|---|---:|---:|---:|
| 100% | 960×640 @232.444,90.083 | 960.215×640.146 @同左 | **0.215 / 0.146 / 0 / 0** | 0.999769 | **0.125px** |
| 200% | 同尺寸 @−127.556,90.083 | 同尺寸同左 | **0.215 / 0.146 / 0 / 0** | 0.999769 | **0.125px** |
| 400% | 同尺寸 @−307.556,90.083 | 同尺寸同左 | **0.215 / 0.146 / 0 / 0** | 0.999769 | **0.125px** |

**⚠️ 上表是修复前的读数，其中两项其实是缺陷的证据，不是「做得好」的证据：**

- `delta 0.215/0.146` 来自 overlay 被写成 `960.222px`（比 canvas 的 960 宽 0.22px）。
- `rootScale 0.999769` 是**假缩放**：`stageRect.width`(961.7778) ÷ `stage.offsetWidth`(整数 962)。真实的 `rootScale` 应为 **1**。

这两项在 round-01 只测了 **Emulation 视口变窄**档（此时 stage 未被 CSS transform 缩放），偏差恒定 0.22px，没越界，所以我当时判成 PASS。但同一套公式在 **transform 缩放档**下偏差会线性放大，400% 就变成 0.8611px 并 FAIL（§10.1）。

**修复后（`32141df`，`world-overlay.ts:84` 读 transform 矩阵真实值）**：三档 `diffR` = −0.0069 / −0.0139 / **0** px；`rootScale` 在未缩放时为 1，在 transform 档下为真实的 2 / 4。标签锚点误差 **0.125px** 不变，仍远低于 0.5px 阈值。

**所以「每帧按 canvas 实际 rect 同步 + 折回本地坐标」的思路是对的，错的是 `rootScale` 的取法。** 修的正是取法。

**仍存的隐患**：`overlay` 尺寸依赖 `stage.getBoundingClientRect()`；若将来给 `#stage` 加 CSS `transform: scale()`（§1 方案 A），`rootScale` 会真正 ≠1。修复后的矩阵取法已能正确处理这种情况（round-05 实测 transform 档 `rootScale` = 2 / 4 正确），但 §1 方案 A 落地后仍须复测这条链路。当前 100/200/400% 走的是**视口变窄**而非 transform，所以 `rootScale` 仍 ≈1。

**是否触及色预算**：不适用。

> ### 更正声明（2026-10-20T17:32）
>

> 我在 round-01 之后只看到「overlay 已经贴得很准（delta 0.215px）」，就推断断言恒真。但那是**修复之后**的状态。回测修复前的公式，400% 档实测 `contained=false`，**这条断言是真的 FAIL**。如果按原结论把它当假绿删掉，S-L544 这个 bug 今天就不会被发现。
>
> 正确的结论是两条，见本节「结论」。

> **行号已于 2026-10-20T17:06 重新 grep 定位**（该文件未跟踪、曾被改动，旧行号 `:604` 已失效）。对照见本节末「行号对照」。

`scripts/smoke-ego.mjs:780-804` 的「L526-549：100/200/400% 缩放」实现为：

```js
await page.evaluate((value) => {
  const stage = document.querySelector('#stage');
  stage.style.transformOrigin = 'top left';
  stage.style.transform = value === 1 ? '' : `scale(${value})`;   // ← 问题在这
```

### 10.1 这条断言实际抓到了什么：一个真 bug（已修）

断言内容是：

```js
sameWidth && sameOrigin && contained   // 用 getBoundingClientRect 对比 canvas 与 overlay
```

**它不是恒真的。** 我用当前代码回放修复前的公式（把 overlay 宽度按 `canvasRect.width / (stageRect.width / stage.offsetWidth)` 写回）实测：

| 档位 | `stage.offsetWidth` | `stageRect.width` | 旧公式算出的 scale | 旧代码 overlay 渲染宽 | canvas 宽 | **`diffR`** | `contained` 判定 |
|---|---:|---:|---:|---:|---:|---:|---|
| 100% | 962 | 961.7778 | **0.999769** | 960.2218 | 960 | **+0.2083px** | pass |
| 200% | 962 | 1923.5555 | 1.999538 | 1920.4436 | 1920 | **+0.4167px** | pass |
| 400% | 962 | 3847.1111 | 3.999076 | 3840.8873 | 3840 | **+0.8611px** | **FAIL** |

> 与 Chief 独立跑出的 0.215 / 0.431 / 0.861 在常数上略有差异（我在 1440 视口、`stage.offsetWidth=962` 下复现；不同视口下取整基数不同），但**线性放大规律与 400% 越界结论完全一致**。

**修复后**（`32141df`，`world-overlay.ts:84` 改用 transform 矩阵真实值）：

| 档位 | `diffR` 实测 | `contained` |
|---|---:|---|
| 100% | −0.0069px | pass |
| 200% | −0.0139px | pass |
| 400% | **0** | pass |

**根因**（`world-overlay.ts:68` 修复前）：`const rootScale = stageRect.width / stage.offsetWidth;` —— `offsetWidth` 是**整数取整值 962**，`stageRect.width` 是小数 961.7778，相除得 **0.999769**，一个本不该存在的「假缩放」。overlay 宽度因此被写成 `960 / 0.999769 = 960.2218px`，比 canvas 宽 0.2218px；该固定偏差**随 stage 缩放线性放大**，到 400% 变成 0.8611px，越过 `contained` 的 0.5px 容差。

**所以：这条断言有效，且抓到了一个真实的亚像素 bug。不能删。**

### 10.2 它的真实盲区：测不到页面级溢出

transform 档测的是 **overlay 与 canvas 的相对贴合**，它测不到 **页面级横向溢出**。原因是 transform 档的 `scrollWidth` 语义与真缩放不同：

| 档位 | transform 档 `scrollWidth / clientWidth` | 真缩放档（Emulation）`scrollWidth / clientWidth` |
|---|---|---|
| 100% | 1425 / 1425（溢出 0） | 1425 / 1425（溢出 0） |
| 200% | 2155 / 1425（溢出 **730**） | 833 / 705（溢出 **128**） |
| 400% | 3718 / 705（溢出 **3013**） | 653 / 345（溢出 **308**） |

> **顺带更正我早先的一个错误说法**：我原写「transform 不改布局，`scrollWidth` 不被撑大」——**实测是错的**，transform 档的 `scrollWidth` 反而被撑得更大（200% 下 2155）。真正的差别不是「有没有溢出」，而是 **transform 档的 `clientWidth` 恒为 1440 的窗口宽**（它没有被视口收窄），所以它模拟不出「用户放大后可用 CSS 宽度变少」这件事。溢出数值也因此完全不能代表真实用户体验。

**真正的浏览器缩放**是 CSS 视口变窄 + 设备像素变多。用 `Emulation.setDeviceMetricsOverride({ width: 1440/N, deviceScaleFactor: N })` 实测，测出 200% 溢 128px、400% 溢 308px（§2 用的是另一视口口径，数值 113/293）——**这些页面级溢出，transform 档确实暴露不了**。

**附带**：同文件 `:829-842`（以及同构的 `:990-995` 调试面板段）的 390px 断言在 CDP 覆盖失败时会退化成「在大视口下验证」，并写 `reason: 'ego 无 setViewportSize...未测 390px'`。本轮实测 CDP 覆盖**是成功的**（`emulationVerified=true` 三档全过），说明当初的失败属于环境偶发，不该固化为「测不了」。建议改为：覆盖失败即 `failed`，不再降级通过。

### 10.3 结论（两条，不要只留一条）

1. **transform 档：保留，它有效。** 它守的是「overlay 在任意缩放下与 canvas 同框」这条不变量，实测抓到 400% 下 0.8611px 偏差的真 bug（`32141df` 已修）。**删了就会失去 overlay 贴合回归保护。**
2. **页面级溢出：现有 smoke 覆盖不到，需另加 Emulation 档。** 这是**盲区，不是假绿**——断言本身没撒谎，只是它没看守那一块。

### 10.4 修复建议

1. **两种档位都保留**，各测各的：transform 档 → overlay 与 canvas 的相对贴合；`setDeviceMetricsOverride` 档 → 页面级溢出与缩放。**不要把 transform 循环替换掉。**
2. 每档断言加 `emulationVerified`（比对 `window.innerWidth` 与请求值），未生效即 fail。
3. **新增**断言 `document.scrollWidth <= clientWidth`（仅对 Emulation 档有意义；transform 档的 `scrollWidth` 不代表真实体验，见 10.2）。
4. `:829-842` 与 `:990-995` 的降级分支改为硬失败。
5. 给 `contained` 的 0.5px 容差加注释，写明它守的是亚像素贴合，并附 `32141df` 的案例，避免后人误判为「容差太松」。

### 17.2 结论一：「众数带 > 60%」这条判据**已失效**

这是本轮最重要的结论。**判据失效比数据失效严重**：数据过期只误导一次，判据过期会持续误导每一次。

按 §8.1 定下的旧判据（众数带 > 60% 判「一片同亮度」），当前画面 **58.43% 低于阈值，会被判「已解决」**。但同一组数据里 **IQR = 0** —— 中间 50% 的像素完全同值，实际比改色前**更平**。

**失效机理**：

1. 「众数带」是**分桶统计**，16 桶 × 16 级 = 每桶 16 级。一个占屏过半的色只要落在某桶内，该桶占比就高；而它只要稍微跨过桶边界，指标就大幅改善，**画面可以几乎没变**。
2. 更关键的是，众数带占比**只描述「最大那一桶有多大」，不描述「其余像素散不散」**。当画面被单色主导时，这一桶占比高；当画面被两色均分时，这一桶占比反而低——但两种都可能是「一片同亮度」。

**替代判据（建议双指标，两个都要看）**：

| 指标 | 阈值 | 为什么它不会失效 |
|---|---|---|
| **IQR**（连续量） | **≥ 12 视为有层次**；< 8 判「一片同亮度」 | 分位数是连续量，不受分桶边界影响 |
| **单色最大占比** | **> 40% 判「单色主导」** | 直接量「画面被一个色吃掉多少」，与分桶无关 |

按新判据，当前画面 **IQR = 0（远低于 8）** 且 **grass 单色占 50.95%（远超 40%）** —— **两个指标都判「一片同亮度」，且比改色前更严重**。旧判据给出的是相反的结论。

### 17.3 结论二：同亮度的来源变了，从「多色挤一条带」变成「grass 一色占半屏」

当前画面逐色构成（帧 0）：

| 色 | token | 占比 | luma255 | 落在哪条带 |
|---|---|---:|---:|---|
| `#2d3b2e` | **grass** | **50.95%** | 55.08 | **48–63（众数带）** |
| `#1b211c` | soil | 15.96% | 31.36 | 16–31 |
| `#3e433f` | stone | 9.34% | 65.65 | 64–79 |
| `#3b3423` | farm | 6.60% | 52.26 | 48–63 |
| `#4a4f42` | plaza | 4.73% | 77.00 | 64–79 |
| `#8a5a44` | timber | 1.68% | 98.62 | 96–111 |

**`grass` 一个色占 50.95% 画布，它的 luma 55.08 落在 48–63 带内。** 于是 q1、中位、q3 全部落在同一个 grass 像素值上 —— `IQR = 0` 是这么来的，不是测量故障。

**这与改色前的成因完全不同**：

| 阶段 | 「一片同亮度」的成因 | 正确解法 |
|---|---|---|
| 16 色阶段（§8.1b/§8.1d） | 4 个地形基色挤在同一条带（grass 55.08 / stone 61.65 / farm 52.26 / grassLit 61.80），覆盖 65% 面积 | 把一个基色推出带边界（调 stone） |
| **24 色重建后（本节）** | **grass 单色占 50.95%，画面被一个色吃掉一半** | **让 grass 内部产生明度层次**（纹理/明暗分区/材质变化），调 stone 或调 plaza 都无效 |

> **这条推翻了此前「调 stone 或调 plaza」的思路。** stone 现在只占 9.35%，把它调到任何亮度都动不了 IQR —— 因为 q1/中位/q3 由占半屏的 grass 决定。
