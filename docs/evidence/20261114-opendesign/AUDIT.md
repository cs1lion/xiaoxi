- 日期：2026-11-14
- **范围：只做 Web 桌面端**（1280×800 / 1440×900 / 1920×1080）。移动端按你的决定**移出范围**，`chat-mobile*.png` 仅作历史留档，不进结论、不进门禁。

## 2. 确认成立的 6 个问题

### W1（P0）侧栏内容在 1280/1440 被截掉 211 / 111 px，且滚动条只有 1px

- 证据：`.side` `clientHeight=800/900`，`scrollHeight=1011`；`offsetWidth-clientWidth=1`（自定义细滚动条，几乎不可见）。
- 后果：`.side-footer`「慢慢来，我们不赶时间。✳」在 1280/1440 **完全看不到**；记忆面板底部操作（`刷新`/`清空`/第 3 条记忆）压在折线附近——就是你截图里"下半截被切断"的那块。
- 这是**默认笔记本分辨率（1440×900 / 1280×800）下的常态**，不是边缘情况。

### W2（P0）9–11.5px 微字号共 191 处，1 处实测不达标

- 证据：`kicker` 9px、`.plate-head` 7px、`composer-foot .hint` 9px、记忆元信息 9.5px、`此刻` 8.5px。
- 唯一经复核确认真实可见的低对比：**`此刻` 8.5px，`rgb(155,122,62)` on `rgb(242,234,218)` = 3.35:1**（要求 4.5:1），位置 `x=350,y=779`（1440×900）。
- 复核方法：`elementFromPoint` 命中测试，排除 `[hidden]` 子树（`#starmapMount` 里那三个 1.08:1 的"放大/缩小/复位"是误报，已剔除）。

### W3（P1）形象卡比例随屏高漂移：0.81 → 0.70 → 0.57

- 证据：`plate-inner` 高 471 → 543 → 723，宽只有 381/412；同一张 VRM 在 1080 屏被拉成瘦长条，取景与 800 屏完全不同。
- 影响：形象是产品主视觉，取景不锁定意味着**每台机器的"小溪"长得不一样**；也解释了为什么 1080 下人物更小。

### W4（P1）宽屏没有内容宽度上限

- 证据：composer 在 1920 宽 **1524px**（1440 是 1044），`#textInput` 796px；主栏文字随之拉宽，但没有 `max-width`/`ch` 约束。
- 影响：超宽屏上输入行与正文行长失控（阅读行宽 >100 字符），视线跨度大；右侧形象卡却被推到 x=1451。

### W5（P2）行内小按钮 21×19 / 21×23

- 证据：`停用`/`忘掉` **21×19**（3 组共 6 个）、`刷新`/`清空` 21×23、`memHistory` 复选框 12×12。
- 桌面是鼠标环境，严重度低于移动，但「忘掉」是不可逆硬删入口，仍建议给到 28–32px 高 + 8px 间距。

### W6（P2）首屏底部空隙随屏高放大（146→161→209px）

- 证据：`welcome` 底边到 composer 顶边。形象卡底边固定在 `plateToComposer=44`，但左栏内容不跟着长。
- 影响：1080 屏首屏下半部明显发空，「空」得很均匀但不"稳"。

## 3. 成立但不算问题（避免过度修）

- 58px 大标题 + 66px 行高、7–9 字/行：这是「编辑感」的核心，不改。
- 印章骑缝（`.plate-seal{right:-9px;bottom:-9px}`）是有意设计，不动。
- `<a>`/`<button>`/`aria-label`/`role="log"`/`prefers-reduced-motion`（16 段）/`:focus-visible`（11 条）都已到位；键盘 Tab 12 个控件全部可见焦点。
- `#stageFx` 全屏 canvas + 8 个常驻动画：历史 d3d11 探针 ~59 FPS，**当前没掉帧**，只作余量优化。

## 4. 一句话

桌面端的短板不是"不好看"，是 **1440×900 这个最常见尺寸上，侧栏有 111px 内容根本看不见**，以及一整套 9–11px 的字在替设计"省空间"。这两件修完，比加任何动效都值。
