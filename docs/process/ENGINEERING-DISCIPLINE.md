# 工程纪律 · 每条会话的通用原则

**定位**：`AGENTS.md` 的细则页。`AGENTS.md` 只留可执行清单并指到这里；协议红线、
不可逆操作、设计约束仍以 `AGENTS.md` / `docs/AGENT_PLAYBOOK.md` / `docs/PROTOCOL.md`
为准，本文件不复写第二份。

**适用**：所有角色、所有会话、所有改动（含只改文档）。不适用时按 §7 显式标 `skip`。

**状态**：2026-11-08 起生效。

---

## 0. 优先级

1. 协议红线与不可逆操作红线（`AGENTS.md`、`docs/AGENT_PLAYBOOK.md` §「开工前协议红线确认」）
2. 本文件的通用原则
3. 上游 skill（grilling / tdd / poteto-mode）的默认做法

冲突时向上服从。任务卡要求 `docs/prompts/TASK_SHARPEN.md` 的验收 A–E 时，
本文件与它是同一套判据的不同表达，按任务卡执行，不另立标准。

---

## 1. Grill：重大决策先压力测试

**适用**：方案、设计、架构、技术取舍、不可逆或爆炸半径大的改动、需求模糊、
要在多个方案中选择、用户的第一句话可能只是手段而非目标。

**不适用**：纯措辞、错别字、单行修复、已有明确验收标准的机械执行。跳过要写理由。

**要做**：

- 把决策画成设计树，每轮只问「前置条件已经确定」的问题；每题给推荐答案，
  等用户回答后再问下一轮。参考 `.agents/skills/grilling/SKILL.md` 的轮次与 frontier 格式。
- 事实自己查（文件、命令、文档），不把查资料推给用户；属于用户的设计选择列成
  编号问题，不替用户拍板。
- 动手前写出三行：**前提**（必须为真方案才成立）、**反例**（至少一个会让方案失败的
  现实场景）、**失效条件**（出现什么信号就回滚或换方案）。
- 不顺着用户第一句话直接实现；先确认「真正要的结果」与「哪些约束其实不服务目标」。

**可验证判据**：

- 任务卡或首条回复里有「前提 / 反例 / 失效条件」三行；缺一行视为未完成 grill。
- 未决的用户决策是编号问题，不是已替他选好的方案；已查事实注明 `file:line`、提交号或命令输出。
- 小任务写 `skip: grilling — <理由>`，不静默跳过。
- 与 A 档自主性的边界：可逆执行不问直接做；**用户该拍的设计选择必须问**，
  这不是「Block on the Human」，而是把决策还给决策人。

## 2. 先红后绿（red:first）

**适用**：纯逻辑、契约、解析、状态流转、协议字段、可廉价复现的 bug；有公共接缝可以断言。

**不适用**：UI、渲染、视觉、性能、真机、外部服务、需要昂贵夹具的场景。这类改用
**断言先行**：先写可观测判据、基线读数和评分口径，再改实现；不能先红就写明原因，
不伪造红灯。

**要做**：

- 先写失败用例，确认它红在预期断言上（贴出失败输出），再写最小实现。
- 一次一个接缝、一片实现，不做「先写全部测试再写全部代码」的横向切片。
- 测试打在公共接口 / 接缝，不测私有实现；期望值来自独立事实（规范、手工算例、
  known-good 字面量），不由实现反推。
- 修 bug 时先跑新用例确认失败原因与目标 bug 一致，再改生产代码。
- 探针本身要能红：用 `scripts/check_probe.py` 的 `probe_self_check()` 四判据
  （破坏版必须红、还原后必须绿、还原逐字节相同、注入真的发生），不把「全绿」当成
  「被测性质成立」。

**可验证判据**：

- 汇报含「改前红：`<命令>` → `<失败断言>`」与「改后绿：`<命令>` → exit 0」。
- 只有绿没有红的，在任务卡 B 栏写 `red: not demonstrated — <原因>`，并附断言先行的证据。
- 不为变绿改弱断言、不迁就错误实现；行为确已变更的，写明变更依据。
- 任务质量口径参考 `.agents/skills/tdd/SKILL.md`；任务卡验收 B 仍按
  `docs/prompts/TASK_SHARPEN.md`。

## 3. 工作可验收性与环境考量

**适用**：任何将被当作结论、交付或「已完成」依据的改动。
**不适用**：只读浏览、不产出结论的探索（但仍不得把未验证结论说成已验证）。

### 3.1 先探测，再承诺

承诺「跑通 / 实测 / 全绿」之前，先判断当前环境是否具备验收能力，至少查：

- 解释器与依赖：`.\.venv\Scripts\python.exe` 是否存在、关键包能否 import；
- 外部能力：`LLM_API_KEY` 是否配置、模型 / 语音栈文件是否在、网络是否可达；
- 运行时：端口 8000 / 8010 是否有服务在跑、服务是否健康；
- 夹具：浏览器回归需要的本地服务与数据是否就位；
- 数据面：是否允许读写真实库（不允许就只用只读或临时库）。

缺能力就明确写 `未验证` / `[需人工]` / `not_measured: <原因>`。**不得用 Mock、
合成帧、估算值或默认值冒充实测。** Mock 只能证明代码路径能跑，不能证明真实链路、
真实质量或真实性能；两者在汇报里分开写。

**可验证判据**：报告有「环境探测」段（命令 + 输出，或明确缺失项）；每个「已验证」
结论都能指到对应命令或证据；出现 Mock / 合成数据时必须标注，未标注即视为冒充。

### 3.2 同口径前后读数

- 验收必须给**改前 / 改后同一命令、同一配置、同一数据集**下的读数；只给改后数字不算。
- 注明数据集性质（真实 / 合成 / 标注 / 抽样）与样本量 N；**合成标注集不得当生产
  基准或上线依据**。
- 基线不可复现时，说明原因，并给最接近的替代读数与差异来源。

**可验证判据**：汇报含「before / after / 命令 / 数据集 / N」五项；缺一项标
「未验证」。质量或性能结论必须带 N 和分布（至少通过率，或 min / median / max）。

### 3.3 证据落盘

- 证据写到 `docs/evidence/<YYYYMMDD>-<topic>/`（命令输出、日志、截图、报告），
  或任务单明确指定的位置；口头汇报、聊天记录不算受检证据。
- `docs/process/trail.jsonl` 的 `evidence` 与 `verification` 仍按
  `scripts/check_process_trail.py` 的要求填，不因本文件放宽。

**可验证判据**：每个「完成」结论在报告里有一个可打开的路径；路径不存在或为空，
即未完成。

## 4. 工作流 / Skill 改造四标准

**来源**：图片「Skill 自迭代能力改造指南」（结构清晰 · 工具可靠 · 可验证 · 可改进）。
图片只展示到「改造目标」，**后续步骤不可见**；本文件只落实可见的「使用方式 + 四条
标准」，不补编没看到的流程。

**改造目标**：把工作流从「一份依赖执行者理解和临场判断的操作说明」，变成
「结构、工具、验收、复审都可检查的工作系统」。对应图片的使用方式：把本文件与目标
Skill 路径一起交给有编辑权的 Agent，先读现有文件、再诊断、再与用户确认标准，最后实施。

**适用**：新增或修改 skill、脚本化工作流、prompt 模板、任务模板、检查器。
**不适用**：用完即弃的一次性调试命令；但一旦被写进文档当作流程，就适用。
代码本身的改造（复用优先、先诊断后微创、反补丁叠加）仍按
`docs/AGENT_PLAYBOOK.md` §「工程纪律」，本文件不复制。

### 4.1 改造前先做四步

1. 读现有文件全文（skill / 脚本 / 模板），不只看名字或摘要；
2. 给简要诊断：现状、缺口、爆炸半径；
3. 与用户确认标准与范围：四条标准如何落地、哪些不适用；
4. 再实施，改完按 §3 验收。

**可验证判据**：首条回复或变更记录里有诊断结论与确认点；跳过确认的写
`skip: <reason>`。

### 4.2 四条标准与判据

| 标准 | 对工作流的要求 | 可验证判据 |
|---|---|---|
| **结构清晰** | 触发条件、适用 / 不适用、步骤、失败处理分离；每条规则只有一个出处，重复处只留指针 | 只读该文件能回答「何时触发 / 何时不用 / 下一步跑什么命令 / 失败看哪里」四格，且每格有原文可指；同一规则被复制到第二处即不合格 |
| **工具可靠** | 每条指令用当前环境真实存在的命令、工具、路径；不存在的依赖标 `skip: <reason>`，不让执行者猜工具名 | 步骤逐条在本机跑一次并记录退出码；出现「命令不存在 / import 失败」即不合格；跳过必须显式，不得静默，也不得为了跑通去装依赖 |
| **结果可验证** | 每个工作流至少有一条可执行验收：退出码、断言、快照差异或日志判据；不接受只有「应检查 / 确保 / 注意」的文字 | 把验收命令原样复制能跑出 pass / fail；关键门禁要能给出负例（破坏版应红，必要时用 `probe_self_check()`）；报告附输出 |
| **可改进** | 记录基线、已知失败模式、复审条件（时间或触发信号）、归属与落点；反馈到来时在原文件修订，或显式标记取代旧条目 | 文件内有「何时重审 / 什么信号说明该改」；新规则取代旧规则时有 `supersedes <旧条目>` 标记，不新开平行文档 |

### 4.3 对本项目的硬要求

- 新增或修改任何工作流（skill、prompt 模板、检查脚本、任务模板）必须同时给出
  **可执行验收命令**；只有文字描述的，视为未完成。
- 验收命令必须在当前环境真跑一次并记录退出码；缺工具 / 缺依赖写
  `skip: <reason>`，不静默跳过，也不为跑通而安装。
- 改完的规则要能接住下一次反馈：留下「何时重审 / 什么信号说明该改 / 改哪里」，
  让后来者修订同一份文件，而不是另起一套。

## 5. 汇报最小格式

**适用**：任何宣告「完成 / 可交付 / 已修复 / 全绿」的汇报。

完成时至少给齐：

- 改了什么 + 文件路径；
- grill / red:first 是否触发，未触发给理由；
- 环境探测结果（缺什么、因此什么没验）；
- 改前 / 改后同口径读数 + 数据集性质 + N；
- `未验证` / `[需人工]` / `not_measured` 清单；
- 证据路径；
- 验证命令与各自退出码。

**判据**：缺「未验证」清单视为隐瞒；缺证据路径视为未完成。

## 6. 红线的唯一出处

- `[PROTOCOL_REQUEST]` 停工等 Role 0、不得自造 WS 事件 / API 字段：
  `docs/AGENT_PLAYBOOK.md` §「开工前协议红线确认」、`docs/PROTOCOL.md`。
- 改 `server/assistant/executive.py`、重启 8000 / 8010、删数据、强推共享分支：
  `AGENTS.md`「仍然要停下的」与「项目叠加的额外红线」。
- 验证命令：`docs/TESTING.md`；任务卡验收 A–E：`docs/prompts/TASK_SHARPEN.md`。

本文件只指路，不复制条文。发现冲突时先停下报告，不自行改红线。

## 7. 不适用与豁免

- 任何原则不适用时，写 `skip: <principle> — <reason>` 并在汇报里列出；静默跳过视为违规。
- 纯文档措辞、错别字、单行注释：grill 与 red:first 可 `skip`，但 §3 的「不冒充实测」
  与 §4 的「工具可靠」仍适用（至少跑受影响的文档检查或链接检查）。
