# 像素世界 · 宏观架构笔记

> **历史提案（2026-10-19 标注）**：本文结论「不引成熟引擎、v1 用 Canvas 2D」未被采纳。实际实现采用 **Phaser 3 + Vite + TypeScript**（`pixel-world/`），依据 `PROJECT_BRIEF.md:10` 的已确认决策；背景与 ADR 见 `docs/DECISION_TRAIL_20261019.md` D1。

2026-10-18 · 接 `PIXEL_WORLD_RESEARCH.md`，只谈架构与取舍，未改代码

## 0. 一句话

**你要的不是"一个游戏引擎"，是"一个世界运行时 + 一套受约束的生成器"。**
引擎只解决画得快，世界怎么跑、怎么长、怎么被神谕改变，引擎一行都不给你。

---

## 1. 先把"引擎"这个词拆开

你说的三件事其实落在三个不同的层，混在一起才会觉得"得找个引擎"：

| 层 | 它管什么 | 现成方案能给多少 | 我们真正需要自己写的 |
| --- | --- | --- | --- |
| **渲染内核** | 把 tile / 精灵画到屏幕上，粒子、shader、缩放 | 几乎全部 | 很少（选型问题） |
| **世界运行时** | tick、场景与槽位、角色行为调度、天气、规则、投影 | 一部分（Phaser 有 scene/tilemap/tween；Pixi 没有） | 大部分 |
| **造物主（生成）** | 按规格造房间、摆家具、配光、校验 | **0** | 全部 |

结论：**选型要按"渲染内核"来选，不要指望引擎替你管世界。** 世界运行时的形状由产品决定，任何引擎都不会替你长出来。

---

## 2. 引擎选型：四个硬约束先摆出来

这个项目的特殊之处（不是普通网页游戏）：

1. **没有构建步骤**：`web/` 是原生 ES module + importmap，`package.json` 里只有测试脚本，three 是 vendored 的。引入引擎不能顺手把 Vite/Webpack 带进来（会牵动 50+ 个浏览器测试）。
2. **文本必须是 DOM**：中文排版、可访问性、纸面 UI（任务说明、验收卡、设置）都靠 DOM。canvas 里画中文等于把这三样全丢掉。
3. **真相源在 Python**：台账、状态机、Worker 都在 FastAPI 里，前端只是投影。跨运行时同步是负债。
4. **角色是"3D 渲 2D"**：需要一块 WebGL 离屏（three.js render target），不是纯 2D 素材。

| 方案 | 包体量级 | 和四条约束的冲突 | 结论 |
| --- | --- | --- | --- |
| **Godot 4（Web 导出）** | 数 MB wasm + pck | 开线程要 **COOP/COEP 跨源隔离**，一旦加上，整站的跨域资源和外链都要跟着改；单线程导出官方承认有音频问题；canvas 里没有 DOM 文本；GDScript↔Python 两套运行时 | **v1 出局** |
| **Unity WebGL** | 更大 | 同上，再加许可与加载时间 | 出局 |
| **Phaser 3** | ~1MB gzip | 会接管自己的 loop/input/scene，和现有 rAF、语音播放抢调度；但 Tiled、相机、tween、粒子、音频全都现成 | **备选**：只在"两周要看到活的世界"时用 |
| **PixiJS v8** | 120–250KB gzip（可 tree-shake） | 只管画，没有 scene/physics/audio；正好——我们不需要 | **推荐作为渲染后端（第二阶段）** |
| **Canvas 2D 手写** | 0 | 粒子/雨幕/光要手搓 | **v1 起步** |

### 我的建议

**不引成熟引擎。** 分两步：

- **v1：Canvas 2D + 自研 world runtime。** 一屏 480×300、30×19 块、角色 ≤6、精灵 <200，2D canvas 绰绰有余，且零构建、零新依赖。
- **v2：渲染后端可换 Pixi。** 触发条件写清楚：精灵 >500 / 需要 shader 天气与光照 / 需要 WebGPU。因为 runtime 和渲染是解耦的，换后端不动世界逻辑。

Phaser 留作"如果三周内必须有个能跑的东西"的快速路——它能省掉相机、tween、Tiled 这几块，但会把世界运行时的形状绑死在它的 scene 上，后期拆不掉。

**Godot 唯一真正吸引人的地方是编辑器**（画场景、摆物件）。但这个优势在我们这里被"造物主要自动生成"抵消了——如果场景是生成出来的，编辑器就没那么重要；而 COOP/COEP 的代价是立刻要付的。

## 3. 世界运行时（自己写的那部分）

```
tick 10Hz ──► behavior 调度 ──► 位置/朝向 ──► scene 快照 ──► 渲染(12fps 插值)
   ▲                                              ▲
   └──── rules（避雨/围观/下班/抬头）              └──── project(后端事件)
```

必须有的六件东西：

1. **固定步长 tick**：逻辑 10Hz、动画 12fps、渲染跟着屏幕。像素风的低帧率是风格，也是省电。
2. **区域 + 槽位**：世界不是自由摆放，是"区域 → 槽位"。院子 / 工坊 / 机房 / 街角 / 神殿，每个区域有固定数量的槽（工作台 ×2、货箱 ×1、灯 ×3）。**这是"不会太杂乱"的技术保证**。
3. **行为状态机**：`idle / walk / work / report / shelter / watch`。六个够用，多一个都会失控。
4. **天气与时段**：一个 0–1 的插值状态（晴/雨/雪 + 清晨/正午/黄昏/夜），10 秒渐变，不做秒切。
5. **规则**：下雨 → 户外 actor 走 `shelter`；神谕落地 → 全场 `watch` 抬头 1.5 秒；任务完成 → 对应铺子 `report`。规则是**本地跑**的，不花 token。
6. **校验器**：世界快照必须能过一遍校验（像现在的 `check_protocol.py`）：槽位不越界、角色不重叠、调色板不超 16 色、每区可交互物 ≤8。生成器产出不合格就降级到模板。

**世界预算（写成常量，不许破）**：3 个区域 / 6 个常驻角色 / 每区 8 个可交互物 / 12–16 色 / 4 种天气 / 每角色 4 个动画槽（idle·walk·work·report）。

## 4. 造物主：不是画师，是"施工图 + 装修队 + 审图员"

这是你想法里最有意思、也最容易做坏的一块。我的判断很明确：

> **不要让 LLM 生成像素，让它做选择题。**

理由：像素图不可复现、不可缓存、不可回滚、风格必漂；而"选哪个模板、填哪个槽、用什么调色"是离散的、可校验的、可缓存的。**造物主的产出应该是 JSON 场景描述，不是图片。**

四层结构：

| 层 | 谁定 | 内容 | 可变性 |
| --- | --- | --- | --- |
| **L0 世界规格** | 人（写死） | 网格 16px、逻辑分辨率 480×300、调色板上限、区域与槽位表、角色比例 | 不可变 |
| **L1 房间模板** | 人（手写 3–5 个） | 院落 / 工坊 / 机房 / 街道 / 神殿，各带槽位图 | 很少变 |
| **L2 组件库** | 人（手绘或 CC0） | 语义化素材：`desk / forge / crate / lamp / puddle / banner`，每个带尺寸与锚点 | 持续扩充 |
| **L3 生成器** | LLM | 输入"这周该长什么样 / 神谕说了什么"，输出"用哪个模板 + 填哪些槽 + 用哪套色 + 天气" | 每次可不同 |

生成物走一条固定管道：**LLM 出 JSON → 校验器 → 缓存 → 运行时实例化 → 落进世界记忆**。
校验失败就退回 L1 模板，世界永远不会变成一坨。

这条路线和项目现有哲学一致：`config/*.yaml` 是契约，代码只认契约；造物主同理，它只是一个"更会写契约的组件"。

## 5. 神谕通道：用户怎么"影响世界"

你说的"神"这个设定是聪明的——它一举解决了"没有键鼠操作"的交互真空。但要做对，得有三条纪律：

1. **神谕是显式模式，不是每句话。** 日常闲聊不改变世界；只有"派活 / 改世界 / 召见"才算神谕。否则世界会被你说的话淹没。
2. **神谕只能落成白名单 op。** 不是"理解成什么就做什么"，而是解析到一个固定动词表，参数走 schema 校验：

| op | 例子 | 持续 | 可观察回响 |
| --- | --- | --- | --- |
| `set_weather` | "下起雨了" | 10–30 分钟自动退场 | 雨幕、水洼反光、户外角色进屋、屋檐滴水 |
| `set_time` | "天黑了" | 到下个时段 | 窗灯亮、影子拉长 |
| `place_object` | "院子里多一棵树" | 永久（进记忆） | 落地动画 + 落位阴影 |
| `summon_actor` | "叫营造匠来" | 一次 | 角色从小路走过来 |
| `open_area` | "开一间新铺子" | 永久 | 施工动画 → 新区域解锁 |
| `dispatch` | "帮我把便笺整理一下" | 走状态机 | 便条飞进对应铺子 |

3. **每次神谕必须有回响（神迹）。** 钟声、云影掠过、众人抬头、灯一盏盏亮——这是"用户在屏幕外也能感到被听见"的唯一方式。没有回响的神谕，等于没发生。

另外两条提议：

- **神谕石板**：神殿里一块石板，记录你最近十条神谕和它们的执行结果。它同时是日志、是回执、也是"她记得你说过什么"的证据。
- **可撤销**：最近一条结构类 op 允许"收回神谕"。人会手滑，世界不能被手滑玩坏。

## 6. 关于"资源奖励"：不要货币，要"世界记忆"

你说资源可以后续再做——我的建议是**干脆不要做货币**。

- 货币必然带来"最优解"和"通胀"：要么攒着不花（无聊），要么精打细算（Habitica 式负担）。
- 改成**累积式改变**：每次交付，世界多一件东西——一台新机器、一盏灯、一株植物、墙上一张画。不可花掉、不贬值、不复利。
- 再进一步，做成**三选一**：交付后从"加一盏灯 / 添一盆花 / 换一块招牌"里选一个。这不是消费，是**塑形**——世界因此越来越像"你们俩的"。

这条比任何经济系统都更能兑现"她在长大、世界在长大"。

## 7. 声音：walla 是对的，但要留一条可读的退路

- **walla（哇啦哇啦）**：文本 → 音节序列 → 每个角色一套音色的 blip 音素。不需要 TTS，零延迟，且天然符合像素美学。
- **报纸**：每天一份"晨报"（纸面 DOM），把昨夜发生的事、交付的战果、花了多少 token 写成三条短讯。这是你能真正读到的汇报。
- **TTS 归位**：不是删掉，是**收窄**——只用于"她私下对你说的话"（夜里、贴耳、读日记）。公开播报改成 walla + 报纸。
- **可访问性红线**：walla 不可读，所以凡是 walla 说过的内容，必须有一处文字（报纸 / 石板 / 可展开字幕）。否则读屏用户直接被排除。

## 8. "没有任务时的极大自由度"怎么跑而不烧钱

这是最容易翻车的一条。我的建议：

- **行为树本地跑**（免费）：`闲逛 → 看云 → 浇花 → 打盹 → 擦桌子`，由时段、精力、天气驱动。
- **LLM 当编剧，不当马达**：每 5–10 分钟问一次"她现在想做什么"，产出一两句意图，写进黑板，由行为树去执行。**不是每一帧问模型。**
- **对话只在被接近时生成**：你走近/点她，才调用模型；否则她只发 walla 和动作。
- **预算闸门**：每日 token 上限。超了就切纯行为树模式——世界会变"安静"，但不会坏。

一句话：**自由度来自规则的数量与组合，不来自模型的随机性。**

## 9. 风险与三个验证实验

新增的三条风险（除了上一份里的可读性/游戏化反噬/效率倒退）：

- **P0 造物主漂移**：生成器每次产出不同风格，世界三个月后变成拼贴画 → 靠 L0 规格 + 校验器 + 调色板上限兜住。
- **P1 神谕噪音**：什么都算神谕，世界天天变 → 显式模式 + op 白名单 + 天气类自动过期。
- **P1 walla 可读性**：信息只存在于声音里 → 报纸/石板兜底。

**建议按这个顺序做三个便宜实验，每个都能单独否决方向：**

| 实验 | 做什么 | 多久 | 否决条件 |
| --- | --- | --- | --- |
| **E1 一屏能不能读** | 用纯 HTML/CSS 拼一屏 480×300 的假世界（不做动画），看能不能 3 秒答出"我的事办到哪" | 1 天 | 需要盯着看才懂 |
| **E2 3D 渲 2D 像不像** | 把现有 VRM 渲成 48×64、量化到 16 色，看脸/发/衣是否还认得出是她 | 1–2 天 | 认不出，或像贴纸 |
| **E3 像不像活着** | 一个角色 + 4 个行为 + walla + 一次下雨，跑 5 分钟 | 2–3 天 | 看久了像屏保 |

E2 是这三个里最关键的一个——**如果"像素化的阿栖"不好看，整个方向就得换美术路线**（改为手绘 sprite 或 2.5D），而那会改变工期。
